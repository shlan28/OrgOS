# 项目中心 · 「项目规范」后端 - 技术方案

> 创建日期：2026-10-28
> 状态：**已实现**（2026-10-28）

## 0. 结论（已按推荐值实现）

**规范不进每轮用户消息，而是写进项目工作区的 `AGENTS.md`。** DSH 会在会话开始时把它作为持久基线加载一次；每轮重新拼接用户消息会重复计费、破坏前缀缓存，还会稀释当前指令。

| # | 决策 | 推荐 |
|---|---|---|
| 1 | 注入位置 | 项目工作区的**项目级** `AGENTS.md` 受管区块（保留文件里其他内容） |
| 2 | 长度预算 | 单份 ≤ 16 KB、全部入提示词规范 ≤ 32 KB（UTF-8 字节），低于 DSH 默认 64 KB |
| 3 | 超长规范 | 允许保存，但**不能加入提示词**；提示放入项目知识库或拆成多条，不做静默截断/摘要 |
| 4 | 权限 | 成员可看/编辑未入提示词的规范；**已入提示词的规范只有项目负责人 / 管理员可编辑和开关** |
| 5 | 生效时机 | 规范变更时同步；每轮启动前再校验一次。DSH 恢复会话会对账基线，通常下一轮生效，兜底新会话 |

> **2026-10-28 实现记录**：以上推荐值均按方案落地。规范正文以 SQLite `project_specs` 为真相源，`AGENTS.md` 为受管投影；单份 16 KB / 合计 32 KB；已入提示词规范仅负责人 / 管理员可编辑和开关。

## 1. 现状

- 后端完全没有规范表与路由；当前 Agent 的 `workdir` 是项目工作区，会话由 `runner.startTurn` 每轮启动一次 dsh 进程。

## 2. 关键约束：DSH 怎么加载 AGENTS.md

本仓库依赖 `@deepseek-ai/dsh-agent-instructions`，实测规则：

- 会话第一次请求时加载一条**持久基线**：
  1. `$DSH_HOME/AGENTS.md`（用户全局）
  2. `<agentsHome>/AGENTS.md`
  3. 项目根到会话 cwd 的每一级目录中的 `AGENTS.md` / `CLAUDE.md` / `*.local.md`
- 默认预算 **64 KB**（`maxBytes: 65536`），单文件读取上限 1 MB；超预算时先丢弃宽泛文件，再截断最具体文件，并给出可见提示。
- 加载一次后留在派生历史里，直到压缩；**不会持续监听外部编辑**，但「恢复会话会对账基线」，成功读写文件也会触发重新发现。
- `CLAUDE.md` 与 `AGENTS.md` 内容完全相同时只渲染一次，不需要双写。

结论：规范应该写进 `AGENTS.md`，让 dsh 自己做「会话级持久上下文」，而不是我们每轮拼 prompt。

> 注：本机当前 Agent 的 `workdir` 是应用仓库根目录；真实项目里应是各自的项目工作区。方案按「每个项目一个工作区」设计，共享工作区作为已知边界写在 §12。

## 3. 方案对比

| 方案 | 做法 | 问题 |
|---|---|---|
| 每轮拼进用户消息 | 每轮把规范拼在 `用户问题` 前 | 每轮重复计费；规范变长会稀释本轮指令；前缀缓存失效 |
| 每轮工具检索（RAG） | 规范进知识库，按需检索 | 规范是「必须遵守的约束」，检索漏掉就等于没生效 |
| **写入 AGENTS.md** | 变更时合成受管区块，dsh 会话级加载一次 | 需要处理预算、文件保护、多 Agent 同步；**推荐** |

长规范不放进提示词：提示词是「约束」，不是「资料库」。长资料应进项目知识库（后续可把非提示词规范也索引进 KB）。

## 4. 数据模型

### 4.1 真相源

| 数据 | 存在哪 | 是否真相源 |
|---|---|---|
| 规范正文 / 名称 / 说明 / `inPrompt` | SQLite `server/data/app.db` 的 `project_specs` 表 | **是** |
| `AGENTS.md` 受管区块 | 项目工作区 `<agent.workdir>/AGENTS.md` | 否，由 DB 派生，可随时重建 |
| 预览切段 `content[]` | 浏览器内存 | 否，由 `markdown` 派生 |

**规范正文是落库的**（`project_specs.markdown`）；不落库的只有「预览切段」和「给 Agent 的 AGENTS.md 投影」，两者都能从 DB 重新算出来。

> 与云端总体方案的差异：总体方案把规范定义为 workspace 文件（git 为真相源，DB 只做索引）。当前应用里规范是在 UI 里新建/编辑的，没有独立的项目文件库，因此以 SQLite 为真相源更直接；后续云端有多项目 workspace 与 git 历史时，再切成「文件为真相源 + DB 索引」，AGENTS.md 仍是投影。

### 4.2 表结构

`server/db.js` 新增（`CREATE TABLE IF NOT EXISTS`）：

```sql
CREATE TABLE IF NOT EXISTS project_specs (
  id          TEXT PRIMARY KEY,
  project_id  TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  name        TEXT NOT NULL,                 -- 展示名，如 部署规范.md
  note        TEXT NOT NULL DEFAULT '',      -- 一句话说明
  markdown    TEXT NOT NULL DEFAULT '',
  in_prompt   INTEGER NOT NULL DEFAULT 0,
  created_by  TEXT NOT NULL DEFAULT '',
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  UNIQUE(project_id, name)
);
CREATE INDEX IF NOT EXISTS project_specs_project
  ON project_specs(project_id, created_at);
```

- `content[]` 不落库：预览时前端从 markdown 派生（按 `##` 标题切段）或用 `react-markdown` 渲染；`AGENTS.md` 同样不存正文，只做投影。
- `name` 同项目唯一，重名返回 409；新建时自动补 `.md`。
- 排序：列表按 `created_at DESC`；提示词内按 `name ASC`，保证合成结果稳定（避免无意义地改写 AGENTS.md）。

## 5. 提示词合成

### 5.1 受管区块

写入 `<agent.workdir>/AGENTS.md`，只替换两个标记之间的内容：

> 这是**项目级** `AGENTS.md`：属于项目工作区、随项目走，优先级高于 `$DSH_HOME/AGENTS.md` 用户全局文件。它不是每个 Agent 私有的提示词——同一工作区的多个 Agent 共享同一份，由项目规范统一派生；Agent 各自有独立工作区时，项目变更会同步到每个工作区。

```markdown
<!-- org-os:project-specs:start -->
## 项目规范（由项目成员维护）

以下是本项目的长期约定，执行任务时应遵守。
若与用户当前指令、系统规则冲突，以用户当前指令和系统规则为准；
与具体路径下的说明冲突时，更具体的路径级说明优先。

### 部署规范.md
生产发布前必须跑全量回归。

<该规范的 markdown>

### 接口约定.md
<该规范的 markdown>
<!-- org-os:project-specs:end -->
```

- 标记外的内容原样保留；文件不存在则创建，文件里只有受管区块且规范清空时删除区块（文件随之变空则删除文件）。
- 写入前把规范正文中的 `org-os:project-specs:start/end` 字面量转义，防止规范内容提前闭合区块。
- 原子写：先写 `AGENTS.md.tmp` 再 `rename`，避免 dsh 读到半截文件。
- 合成结果做 hash；与上次一致则不写。

### 5.2 同步时机

| 时机 | 动作 |
|---|---|
| 新建 / 编辑 / 删除 / 开关规范 | 同步到该项目的**所有 Agent 工作区** |
| `runner.startTurn` 启动 CLI 前 | 同步当前 Agent 工作区（hash 相同则无 IO 写入） |
| Agent 新建 / 绑定项目 | 同步一次 |
| 服务启动 | 不主动扫；第一次会话/变更时同步 |

### 5.3 为什么不是每轮注入用户消息

- dsh 的基线只追加一次，位于可复用前缀之后；规范不变时 KV Cache 一直命中。每轮拼用户消息会让前缀每轮变化，成本和不稳定性都更高。
- 规范是「会话开始时就应该知道」的约束，不是「每轮重新提醒」。

### 5.4 生效时机

- 规范变更后，下一轮启动 CLI 前文件已更新；dsh 恢复同一会话时会对账基线，通常下一轮生效。
- 如果当前 dsh 版本没有对账到外部改动，则新规范在**下一个新会话**生效。UI 在开关/保存后提示「已写入项目提示词，将在下一轮或新会话生效」。
- 不在轮次进行中热改文件；`startTurn` 前同步即可。

## 6. 长度与预算

DSH 默认 64 KB 要同时容纳用户全局、仓库自带 `AGENTS.md` 和我们的区块。留一半余量：

```ts
export const SPEC_PROMPT_MAX_BYTES = 32 * 1024      // 所有入提示词规范合计
export const SPEC_PROMPT_PER_SPEC_BYTES = 16 * 1024 // 单份
```

- 用 `Buffer.byteLength(markdown, 'utf8')` 计量（中文约 3 字节/字）。
- 保存时：`inPrompt=false` 不校验长度；`inPrompt=true` 校验单份上限。
- 开关时：校验合计上限，超了返回 400/409，并在 UI 显示当前用量。
- **不静默截断、不做自动摘要**：规范被截断会悄悄改变约束，比拒绝更危险。
- UI：
  - 面板顶部显示「已加入提示词 3 份 · 12.4 KB / 32 KB」；
  - 每行开关 tooltip 显示该文档大小；
  - 超限时行内红字：`该规范 48 KB，超过单份 16 KB 上限；长文档建议放入项目知识库或拆分为多条。`

> 后续可加「规范摘要」能力，但摘要必须由用户确认后才会进入提示词。

## 7. 权限

| 操作 | 项目成员 | 项目负责人 / 组织管理员 |
|---|:--:|:--:|
| 查看规范列表 / 内容 | ✓ | ✓ |
| 新建 / 编辑 / 删除**未入提示词**的规范 | ✓ | ✓ |
| 编辑 / 删除**已入提示词**的规范 | | ✓ |
| 开关「加入提示词」 | | ✓ |

原因：能改已入提示词的规范 = 能改 Agent 的系统级约束，等价于提示词注入权限，不能只按普通文档处理。实现用 `projectRoleOf`（记忆后端已加）。

## 8. API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/projects/:id/specs` | 列表 + 提示词用量 |
| POST | `/api/projects/:id/specs` | 新建 |
| PUT | `/api/projects/:id/specs/:specId` | 编辑（name / note / markdown / inPrompt） |
| DELETE | `/api/projects/:id/specs/:specId` | 删除 |
| PATCH | `/api/projects/:id/specs/:specId/prompt` | 只切换 `inPrompt` |

`GET` 返回：

```json
{
  "specs": [
    {
      "id": "spec_x",
      "name": "部署规范.md",
      "note": "发布前检查",
      "markdown": "...",
      "inPrompt": true,
      "updatedAt": "2026-10-28T...",
      "bytes": 3120
    }
  ],
  "prompt": {
    "count": 3,
    "bytes": 12700,
    "maxBytes": 32768,
    "perSpecMaxBytes": 16384
  }
}
```

校验：

- `name` trim 后 1–120 字，自动补 `.md`；同项目重名 409。
- `markdown` ≤ 1 MB（存储上限，非提示词上限）。
- `inPrompt=true` 时校验 §6 预算，超限 400，body 带 `{ error, bytes, maxBytes }`。
- 每次写操作后调用 `syncProjectSpecs(projectId)`，并返回最新用量。

## 9. 前端改造

- `SpecsPanel` props 从 `{ specs, onUpdateSpecs }` 改为 `{ projectId, canManagePrompt }`，内部用 `specsApi` 拉取。
- 新建 / 保存 / 删除 / 开关调接口，成功后重新拉列表；失败在弹窗或行内显示后端错误。
- `updatedAt` 由 ISO 格式化成 `MM-DD`；`content[]` 改为从 `markdown` 派生。
- 顶部 tips 改成：`开启「加入提示词」的规范会写入项目 AGENTS.md，在会话开始时加载；长文档建议放入项目知识库。`
- 顶部增加用量条：`已加入 3 份 · 12.4 KB / 32 KB`。
- 用量条下方常驻一行容量参考：`合计 32.0 KB ≈ 1.1 万汉字 / 3.3 万英文字符 · 单份 ≤ 16.0 KB`。
- 用量条右侧增加 `?` 按钮，弹窗说明：
  - 32 KB ≈ 1.1 万汉字 / 3.3 万英文字符，单份 16 KB ≈ 5 千汉字 / 1.6 万英文字符；
  - 只限制「加入提示词」，规范本身可保存得更长；
  - 为什么限制（AGENTS.md 总预算约 64 KB、避免静默截断、控制上下文成本）；
  - 建议放什么（代码规范 / 架构决策 / 接口约定 / 部署回滚 / 评审安全 / 协作约定）与不建议放什么（README、教程、会议记录、一次性调试、知识库已有资料）。
- 开关无权限时禁用，title 提示「仅项目负责人 / 管理员可修改」。
- 开关后的常驻 toast 文案保留，但补一句生效时机。

## 11. 验收标准

1. 新建 / 编辑 / 删除规范刷新后仍在（落库）。
2. 开启「加入提示词」后，项目工作区 `AGENTS.md` 出现受管区块，内容与规范一致；关闭后区块移除，文件其他内容不变。
3. 两份规范的顺序稳定（按 name），重复保存不产生无意义文件写入。
4. 单份 >16 KB 或合计 >32 KB 时无法加入提示词，返回明确错误，UI 显示用量。
5. 修改已入提示词的规范后，下一轮启动前 `AGENTS.md` 已更新。
6. 成员无法开关提示词、无法编辑已入提示词的规范；负责人可以。
7. 重名返回 409；删除规范后提示词区块同步更新。
8. `npm run build` 通过；非研发项目只存规范，不写工作区。

## 12. 风险与边界

| 风险 | 处理 |
|---|---|
| DSH 64 KB 总预算被其他 AGENTS.md 占用，我们的区块被省略 | 我们的合计上限 32 KB，留一半余量；超限时拒绝加入而不是静默丢 |
| 多个项目共享同一个 `workdir` | 受管区块按项目覆盖，切换项目前同步；并发运行不同项目会互相覆盖。文档标注限制，推荐一项目一工作区 |
| 规范内容包含区块标记 | 写入前转义标记字面量，防止破坏受管区块 |
| 中途改规范当前轮不生效 | `startTurn` 前同步；dsh 恢复会话对账，兜底新会话生效；UI 提示生效时机 |
| 成员通过编辑已入提示词规范注入内容 | 已入提示词的规范仅负责人/管理员可编辑和开关 |
| 长规范被截断后语义变化 | 不做自动截断/摘要；超预算直接拒绝加入 |
| 非研发项目没有 Agent/工作区 | 规范照常存储；不发提示词，UI 标注「该项目暂无 Agent」 |
