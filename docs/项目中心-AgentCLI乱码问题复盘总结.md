# 项目中心 · Agent CLI「乱码」问题复盘总结

> 创建日期：2026-10-22
> 更新日期：2026-10-22

## 0. 一句话结论

格 3「Agent CLI」的内容看起来是乱码，**不是编码问题、不是字体缺字，而是 CSS 类名冲突导致的行布局塌陷**——
`TitleBar.css` 的全局裸类 `.tl`（macOS 红绿灯圆点）命中了终端轨迹条目 `.tl`，把每条轨迹压成 12×12 的
小圆点盒子，26 条轨迹横向流式排列、正文被压成 0 宽，全部叠印在同一水平带上糊成墨带。

## 1. 问题现象

- **位置**：项目中心 → loomweb 详情页 → 格 3「Agent CLI」（`TerminalPane`）
- **现象**：终端区域文字互相重叠、糊成几条灰色墨带，大面积空白，右侧被截断，完全不可读
- **预期**：agent CLI 终端样式，完整展示 agent 思考（◦）、执行命令（❯）、调用工具（⚡）、
  读写文件（▸ 路径 + 内容预览）的全部详细流程，逐行清晰、可滚动

## 2. 诊断历程（含一次误诊）

### 2.1 第一轮：误诊为字体回退问题 ❌

做法：Playwright 提取 `.terminal-pane` 文本 → 内容正常（中文、命令、路径全对）；
测量字体宽度 → 中英字宽比 1.66:1（终端要求 2:1）→ 判定为「字体栈缺 CJK 回退」，
改字体栈补 `Noto Sans Mono CJK SC`。

**为什么错**：只验证了「数据层」和「字体度量」，**没有做 DOM 几何测量、没有逐像素读图**。
字体宽度差异确实存在（是真的，值得修），但它不是乱码的原因，只是叠加在真问题之上的一层干扰。

### 2.2 用户复核 → 否定结论

用户直接指出「这两张图明明是乱码啊」，并给出截图路径。
→ 说明修复无效，必须重新定位。**这一步是问题的转折点**：如果按原结论收工，缺陷会直接流入交付。

### 2.3 第二轮：多手段交叉定位 ✅

| 手段 | 结果 |
|---|---|
| 图片 3 倍放大 + `vision-subagent` 逐像素分析 | 无豆腐块/问号（非缺字）；多行文本**叠印在同一水平带** → 判定为布局塌陷 |
| Playwright DOM 几何测量（每个 `.tl` 的 `getBoundingClientRect`） | 26 个 `.tl` 中 **19 个与前一元素 y 重叠**；x 严格以 **12px 步进**横向排列 |
| computedStyle 溯源（`matches()` 遍历全部样式表） | `.tl` 命中两条规则：`TitleBar.css` 的 `width:12px/height:12px/display:inline-block` + `TerminalPane.css` 的 `margin-bottom:5px` |

三条证据指向同一结论 → 真根因确认。

## 3. 根因分析

```
TitleBar.css      .tl { width:12px; height:12px; border-radius:50%; display:inline-block }  ← 全局裸类
TerminalPane.css  .tl { margin-bottom:5px; flex-shrink:0 }                                   ← 同名裸类冲突
```

- 两个选择器 specificity 同为 **0-1-0**（都是单类），`TitleBar.css` 先注入 `<head>` → 圆点样式生效
- 每条终端轨迹被渲染成 **12×12 的 inline-block 盒子** → 在 `.term-body`（block 容器）里横向流式排列
  （x 从 761 起以 12px 步进，排满约 17 个/行换行）
- 内部 flex 行 `.term-row` 被父盒子 12px 宽度挤压，`.body` 因 `min-width:0 + overflow:hidden` → **文本宽 = 0px**
- 结果：26 条轨迹叠印在 y≈145.6~164.1 与 y≈236.7~248.7 两条水平带上 → **「乱码墨带」**

### 为什么会踩这个坑

- 使用了**全局裸类名**（`.tl`）这种极易冲突的命名，且分散在两个组件
- TerminalPane 的 `.tl` **没有显式声明 `display`**，被其他文件的同名规则静默改写也不报错
- CSS 冲突是**静默失效**：TS/构建/lint 全绿，只有渲染结果错，必须靠视觉/DOM 几何才能发现

## 4. 修复内容（commit `16486c5`）

| 修复 | 文件 | 说明 |
|---|---|---|
| 轨迹条目改名 | `TerminalPane.tsx` / `.css` | `.tl` → **`.term-line`**，`.tl-row` → **`.term-row`** |
| 显式声明 display | `TerminalPane.css` | `.term-line { display: block }` + CSS 注释记录冲突教训，防复发 |
| 冲突源作用域化 | `TitleBar.css` | 红绿灯 `.tl` 及 `.close/.minimize/.maximize` → **`.traffic-lights .tl`**（不再污染全局） |
| 附带修复 | 9 个 CSS 文件 13 处 | mono 字体栈统一补 `'Noto Sans Mono CJK SC' / 'Noto Sans Mono CJK TC'` 回退（Linux 下中英 2:1 等宽对齐） |

设计取舍：采用**改名 + 作用域化双保险**，只作用域化任一侧都可能被后续改动再次引入；
显式 `display: block` 是第三层防护，让同类冲突即使发生也不会静默塌陷。

## 6. 经验教训

### 6.1 「乱码」类问题必须 DOM 几何测量 + 逐像素读图

「乱码」有三种完全不同的成因，必须靠证据区分，不能凭第一直觉下结论：

| 成因 | 特征 | 定位手段 |
|---|---|---|
| 编码/数据错误 | 提文本即见乱字符（锟斤拷、``） | 提取 textContent |
| 字体缺字 | 豆腐块 □ / 问号 / 字宽不齐 | 字体度量 + 截图读图 |
| **布局塌陷叠印** | 文本正常但多行重叠成墨带 | **DOM getBoundingClientRect 几何测量** |

**本次误诊的根本原因**：跳过了第三行的几何测量。

### 6.2 验证结论要「用户视角复核」，不能只看自己提取的数据

第一轮只看了 `textContent`（数据对）和字体宽度（有差异就改），得出「内容没乱码、只是字体问题」——
但用户看到的是**渲染结果**。任何 UI 缺陷的验收标准是**用户看到的画面**，必须亲自读图确认。

### 6.3 静态检查全绿 ≠ 没问题

CSS 类名冲突是最典型的静默失效：tsc 通过、vite build 通过、无 lint 报错，只有像素结果错。
→ 涉及样式/布局的改动，验收必须包含**实际渲染验证**。

### 6.4 防御性写法

- 组件样式优先**加作用域前缀**（`.term-*` / `.traffic-lights .tl`），避免全局裸类
- 关键布局属性（`display`）**显式声明**，不依赖浏览器默认值——默认值被外部同名规则改写时无任何提示
- 组件根类名带上**组件语义前缀**（`term-line` 而非 `tl`），从命名上降低撞名概率

## 7. 遗留与建议

- 项目中仍有其他裸类名（如 `.tl` 已在 TitleBar 侧作用域化，其他组件未做全量审查）
  → 建议后续做一次**全局裸类名冲突扫描**（对比所有 CSS 的类选择器，找出跨文件重名项）
- 本次附带修复的 13 处 mono 字体栈回退，macOS/Windows 端优先命中原字体，无行为变化
