# 项目知识库 · 检索与召回 - 技术方案

> 创建日期：2026-10-28
> 前置：[云端平台-P3-知识库RAG实施-技术方案.md](云端平台-P3-知识库RAG实施-技术方案.md)（设计源）、[项目中心-飞书文档同步-技术方案.md](项目中心-飞书文档同步-技术方案.md)（语料来源）
> 关注点：**召回准确性**。本文档把"怎么衡量召回"和"怎么提高召回"放在第一位，索引与界面次之。

## 0. 决策摘要

| 项 | 结论 |
|---|---|
| 技术栈 | 沿用现有单机 Node + `node:sqlite`，不引入 Postgres / pgvector / 向量库 |
| 全文检索 | SQLite FTS5 `trigram` 分词（中文可用，已验证） |
| 向量检索 | 嵌入结果存 BLOB，查询时在进程内做余弦暴力检索；**嵌入模型可选，未配置时退化为纯关键词** |
| 融合 | BM25 与向量各取 Top 40，按权重 RRF 融合（关键词 1 / 短词 0.8 / 向量 0.35），向量命中需过 0.6 余弦门限 |
| 核心理念 | **先评测，再调优**。没有黄金集和基线数字之前不动检索参数 |
| 本期不做 | 图索引、多模态理解、跨项目联邦检索、微调嵌入模型 |

## 1. 现状与差距

| 项 | 现状 | 差距 |
|---|---|---|
| 语料 | `feishu_doc_contents` 存了每篇文档的最新正文快照（markdown） | 没有切分、没有索引，`kb_state` 停在 `ready` |
| 检索 | 无。知识库子 tab 的「检索测试」按钮置灰 | 需要索引管道 + 检索接口 + 可观测的评测 |
| 前端 | `KbIndexPanel` 显示收录清单与拉取状态 | 需要真实的命中结果、片段预览、评分 |
| 覆盖 | PDF / 思维导图 / 白板不支持正文提取；图片已支持（视觉模型转写，见 §17.9） | **索引不到的内容永远召回不到**，必须在界面上显式暴露覆盖率 |

## 2. 召回为什么会不准（先定义问题）

按本项目语料（飞书产品/研发/会议文档）归纳六类失败模式，后续每个设计点都要能对上其中至少一类：

| # | 失败模式 | 典型例子 | 主要对策 |
|---|---|---|---|
| 1 | **中文分词** | 用户搜「窗格」，文档写「窗格拖拽」 | trigram ≥3 字 + 短查询 LIKE 兜底（§6.1） |
| 2 | **术语/缩写不一致** | 用户写「ADE」，文档写「Agent 开发环境」 | 项目术语表做查询扩展（§6.3） |
| 3 | **切分切断语义** | 一张表格被切成两半，标题与正文分离 | 结构感知切分 + 标题链前缀（§4） |
| 4 | **表格与数字** | 问「Q3 目标是多少」，答案在表格单元格里 | 表格整块保留、重复表头；表格单独可检索（§4.3） |
| 5 | **跨文档引用** | 问「灰度流程」，答案分散在 SOP 与复盘两篇 | 多片段返回 + 父文档回填（§5.4） |
| 6 | **覆盖缺失** | 内容是 PDF / 图片 / 未收录文档 | 覆盖率指标 + 明确的"未索引"提示（§9） |

> 结论：召回不准很少是"模型不够好"，多数是 3、4、6 造成的。所以调优顺序按 §8 执行，而不是先换嵌入模型。

## 3. 总体架构

```
【索引管道】文档 ready 后触发（手动 / 批量 / 同步完成后自动）
  markdown 快照
    → Parser    按标题层级切 Section（保留表格整块）
    → Chunker   Section 内按段落二次切分，带重叠
    → Enricher  生成 context 前缀：文档标题 › 一级 › 二级
    → Embedder  （可选）批量调用 /embeddings
    → 写入 kb_chunks + kb_chunks_fts

【检索管道】
  query
    → 归一化（全半角、大小写、术语扩展）
    → BM25（FTS5）Top 40
    → 向量（可选）Top 40
    → RRF 融合 Top 20
    → 重排（可选，LLM 打分）Top 8
    → 父文档回填 + 相邻片段拼接
    → 返回 {片段, 来源, 路径, 分数, 是否低置信}
```

## 4. 切分方案

### 4.1 规则

1. **结构优先**：先按 markdown 标题（`#`~`###`）切 Section；标题链作为 `section_path`。
2. **长度兜底**：Section 正文 ≤ 800 字符 → 整节一个 chunk；超过则按空行段落聚合到 800 字符左右切分，**片段间重叠 120 字符**，且不跨 Section。
3. **最小长度**：< 40 字符的 Section 向上合并到父 Section，避免产生"只有标题"的碎片。
4. **确定性**：同一份正文必须切出同样的 chunk（`sha1(section_path + ordinal + content_hash)` 作为身份），否则无法增量、无法对比评测。
5. **表格**：一个 markdown 表格是一个原子块，**永不拆分**；超过 2000 字符时按行切分，但每段重复表头。
6. **代码块**：整体保留，超长时按空行切，保留语言标记。

### 4.2 上下文前缀（Enricher）

- 嵌入与全文索引使用 `context`：`{文档标题} › {一级标题} › {二级标题}\n{正文}`。
- 返回给用户时用 `content`（不含前缀），避免重复。
- 目的：解决"多个文档都有『接口说明』"这类歧义，让标题词也能被命中。

### 4.3 参数

| 参数 | 值 | 说明 |
|---|---|---|
| 目标 chunk 大小 | 800 字符（约 400 token） | 中文按字符估，不引 tokenizer |
| 重叠 | 120 字符 | 只在二次切分时产生 |
| 最小合并阈值 | 40 字符 | 过小并入父节 |
| 单篇最大 chunk 数 | 500 | 超出截断并标记 |

## 5. 数据模型

```sql
CREATE TABLE IF NOT EXISTS kb_chunks (
  id              TEXT PRIMARY KEY,
  project_id      TEXT NOT NULL,
  doc_id          TEXT NOT NULL REFERENCES feishu_docs(id) ON DELETE CASCADE,
  revision        TEXT NOT NULL,          -- 来源快照的 revision
  ordinal         INTEGER NOT NULL,       -- 文档内顺序
  section_path    TEXT NOT NULL,          -- 标题链：产品研发/Web 端 › 接口说明
  content         TEXT NOT NULL,          -- 原文片段（返回给用户）
  context         TEXT NOT NULL,          -- 带标题前缀（用于索引/嵌入）
  char_count      INTEGER NOT NULL,
  content_hash    TEXT NOT NULL,          -- 增量判定
  embedding       BLOB,                   -- Float32Array 序列化；未配置嵌入时为空
  embedding_model TEXT NOT NULL DEFAULT '',
  created_at      TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS kb_chunks_doc ON kb_chunks(doc_id, ordinal);
CREATE INDEX IF NOT EXISTS kb_chunks_project ON kb_chunks(project_id);

-- 全文索引：trigram 对中文按 3 字滑窗切分（实测可用）
CREATE VIRTUAL TABLE IF NOT EXISTS kb_chunks_fts USING fts5(
  context,
  content='kb_chunks',
  content_rowid='rowid',
  tokenize='trigram'
);

-- 索引状态：按文档记，便于增量与排错
CREATE TABLE IF NOT EXISTS kb_index_runs (
  id TEXT PRIMARY KEY, project_id TEXT, doc_id TEXT,
  trigger TEXT, status TEXT, chunks INTEGER, embedded INTEGER,
  error TEXT, started_at TEXT, finished_at TEXT
);

-- 评测集与结果（也可只存文件，入库便于按版本对比）
CREATE TABLE IF NOT EXISTS kb_eval_sets (
  id TEXT PRIMARY KEY, project_id TEXT, name TEXT, cases_json TEXT, created_at TEXT
);
CREATE TABLE IF NOT EXISTS kb_eval_runs (
  id TEXT PRIMARY KEY, project_id TEXT, set_id TEXT, pipeline TEXT,
  metrics_json TEXT, failures_json TEXT, created_at TEXT
);
```

- `kb_chunks_fts` 用 external content 模式，写入/删除通过触发器或代码同步 `INSERT INTO kb_chunks_fts(kb_chunks_fts) VALUES('rebuild')`。实现时用显式语句维护，避免 SQLite 版本差异。
- 向量检索在进程内做：`SELECT id, embedding FROM kb_chunks WHERE project_id=? AND embedding IS NOT NULL` → Float32 点积排序。**10 万片段以内可接受**（见 §11）。

## 6. 检索管道

### 6.1 关键词召回（BM25）

```sql
SELECT c.id, bm25(kb_chunks_fts) AS score
FROM kb_chunks_fts f JOIN kb_chunks c ON c.rowid = f.rowid
WHERE kb_chunks_fts MATCH ? AND c.project_id = ?
ORDER BY score LIMIT 40;
```

- **中文长度陷阱（实测）**：trigram 要求查询 ≥ 3 个字符才能命中。
  - 查询长度 < 3（如「支付」「窗格」「鉴权」）→ 走 `content LIKE '%q%'` 兜底，按命中位置与次数粗排。
  - 查询 ≥ 3 → 正常 MATCH；再把整句拆成 3 字窗口，任一窗口命中即可（`OR`），避免长句整串匹配失败。
- Latin/数字：trigram 同样适用（`abc` 会按 3 字切），短英文单词走 LIKE。

### 6.2 向量召回（可选）

- 配置了嵌入模型时：查询向量与项目内片段向量做余弦相似度，取 Top 40。
- 未配置：跳过该路，只跑 BM25。**产品上不阻塞**：纯 BM25 已经是可用的基线。
- 嵌入模型要求 OpenAI 兼容 `POST /embeddings`，维度写入配置；换模型时整库重嵌（`embedding_model` 标记旧数据，后台渐进重建）。

### 6.3 查询归一化与扩展

1. 全角转半角、去多余空白、英文小写。
2. 项目术语表（`org_settings` 或项目配置）做同义词扩展：`ADE → Agent 开发环境`；扩展只进 BM25 查询，不改原查询。
3. 可选（v2）：LLM 改写为 2–3 个查询变体，多路召回后并集去重。

### 6.4 融合（RRF）

```
score(chunk) = Σ_routes 1 / (60 + rank_in_route)
```

取融合后 Top 20；同一文档最多保留 4 个片段，避免单篇霸屏。

### 6.5 重排（可选）

- **优先用专用重排模型**（模型名含 `reranker`，如 `BAAI/bge-reranker-v2-m3`）：走 `POST /rerank`，直接把融合后的候选（最多 20 条）作为 documents 提交，按 `relevance_score` 重排取 Top K。
- 也可以配置普通对话模型：把每条候选截断到 300 字，让模型输出 `[{i,s}]` 打分（0–5）。这条路更慢（6.9s vs 0.69s）、指标更差，仅作兜底。
- 未配置、超时（20s）或返回异常：直接沿用融合顺序，不影响可用性。
- 重排是**提升首屏精度**的手段，对召回率（是否包含答案）帮助有限，不要指望它救召回。

### 6.6 父文档回填与低置信

- 命中片段返回时附带同文档相邻片段（前 1 后 1），帮助阅读上下文。
- 低置信判定使用「**检索探针覆盖率**」：把实际用于召回的词（3 字窗口、短词、2 字兜底）逐条比对首条命中，覆盖率 < 0.3 或零命中 → 标记 `lowConfidence`，前端提示「未找到足够依据」。
- 不使用 BM25 绝对分做阈值——实测小语料里 bm25 只有 -0.58 量级，固定阈值完全不可用；向量命中本身已过 0.6 余弦门限，不再二次判分。
- 返回结构：`{ chunks: [{ docId, title, url, sectionPath, content, score, route }], lowConfidence }`。

## 7. 索引触发与增量

| 触发 | 说明 |
|---|---|
| 文档加入知识库并拉完正文 | 自动切分索引（`kb_state: ready → indexed`） |
| 文档 revision 变化（stale） | 只重建该文档的片段 |
| 手动「重建索引」 | 单篇或全部；全部走串行队列 |
| 移出知识库 / 文档删除 | 级联删除片段与 FTS 行 |

增量判定：按 Section 计算 `content_hash`，未变的 Section 复用旧 chunk 与向量；只有变化的 Section 重切、重嵌。

## 8. 调优顺序（按性价比）

| 顺序 | 手段 | 预期收益 | 成本 |
|---|---|---|---|
| 1 | 切分与前缀（标题链、表格整块） | **最大**，通常决定能否命中 | 低 |
| 2 | 中文短查询兜底 + 术语表 | 高（中文场景常见失败） | 低 |
| 3 | 混合检索（+向量） | 中高（同义改写、语义近似） | 中（需嵌入模型与费用） |
| 4 | 重排 | 中（首屏排序，非召回） | 中 |
| 5 | 查询改写/多路召回 | 中 | 中高 |
| 6 | 换嵌入模型/微调 | 低到中 | 高 |

**每一档都必须用黄金集跑数字**，收益不明显就不上线，避免为"感觉更先进"付运维成本。

## 9. 评测体系（本期重点）

### 9.1 黄金集

每个项目维护一份 `server/data/kb-eval/<projectId>.jsonl`：

```jsonl
{"q":"灰度发布怎么做","expectDocs":["d12"],"expectSnippets":["灰度"],"type":"通用"}
{"q":"Q3 目标","expectDocs":["d4"],"expectSnippets":["目标","Q3"],"type":"表格"}
{"q":"ADE 是什么","expectDocs":["d1"],"expectSnippets":["Agent 开发环境"],"type":"缩写"}
{"q":"没有答案的问题示例","expectDocs":[],"type":"无答案"}
```

- 起步 20–30 条即可，覆盖六类失败模式；每类至少 3 条。
- `type` 用于分类型统计，避免总量好看但某一类全错。
- 无答案题用于衡量"不该召回时的克制"。

### 9.2 指标

| 指标 | 定义 | 用途 |
|---|---|---|
| Recall@5 / @10 | 答案文档出现在前 k 条的比例 | **核心指标**，对应"能不能找到" |
| MRR | 首个正确片段排名的倒数均值 | 首屏体验 |
| nDCG@10 | 排序质量 | 重排前后对比 |
| 无答案误召回率 | 无答案题返回了高分片段的比例 | 防过度自信 |
| 覆盖率 | 已索引文档 / 已收录文档 | 语料侧上限 |

### 9.3 脚本

```bash
npm run kb:eval -- --project <projectId> --pipeline bm25      # 纯关键词
npm run kb:eval -- --project <projectId> --pipeline hybrid    # 关键词 + 向量
npm run kb:eval -- --project <projectId> --json               # 机读输出
```

融合参数可用环境变量做 A/B：`KB_WEIGHT_BM25 / KB_WEIGHT_LIKE / KB_WEIGHT_VECTOR / KB_MIN_COSINE / KB_VECTOR_MODE`。

输出：总指标表 + 分类型指标 + 失败用例清单（问题、期望、实际 Top3），直接用于下一轮调优。

### 9.4 门禁建议

- 首轮只记录基线，不设门槛。
- 达到以下水平再接入 Agent：`Recall@10 ≥ 0.85`、`MRR ≥ 0.6`、无答案误召回 ≤ 15%。
- 每次改切分/模型后必须重跑，指标下降即回滚。

## 10. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/projects/:id/kb/index` | 建/重建索引 `{docId?}`，异步，返回 runId |
| GET | `/api/projects/:id/kb/status` | 覆盖率、片段数、嵌入模型、最近一次运行 |
| GET | `/api/projects/:id/kb/docs/:docId/chunks` | 片段预览（分页） |
| POST | `/api/projects/:id/kb/search` | `{q, topK, rerank?}` → 命中片段与分数 |
| GET/PUT | `/api/projects/:id/kb/config` | 嵌入模型配置（baseUrl/model/dim）+ 术语表 |
| POST | `/api/projects/:id/kb/eval` | 跑评测（也可只用 CLI） |

嵌入 Key 存 `secrets.json`，接口不回传。

## 11. 性能与规模

| 规模 | 方案 |
|---|---|
| ≤ 1 万片段 | 进程内暴力向量检索足够（单次 < 50ms） |
| 1–10 万 | 仍然可用，加 `Float32Array` 批量点积与缓存；索引构建分批 |
| > 10 万 | 再评估 `sqlite-vec` 扩展或外部向量库；本方案不预做 |

索引构建：串行队列，单文档渲染 → 切分 → 批量嵌入（每批 16 条）→ 写库，失败重试 3 次并记录到 `kb_index_runs`。

## 12. 前端改造

「项目知识库」子 tab：

- 状态：`未收录 / 拉取中 / 待索引 / 已索引 / 失败 / 待更新`（未再拆「排队中 / 切分中 / 嵌入中」）。
- 顶部统计增加「片段数」「覆盖率」，覆盖不足时提示哪些文档未索引及原因。
- **检索测试改为真实**：输入框 + Top K 结果列表（标题、路径、片段、分数、来源路由 BM25/向量/重排），低置信时显示「未找到足够依据」。
- 文档详情弹窗增加「片段」页：按 ordinal 列出，可复制，便于人工核对切分质量。
- 索引配置入口：嵌入模型（可留空）、术语表编辑。

## 13. 任务拆解

| 阶段 | 内容 | 产出 |
|---|---|---|
| M1 | 切分器 + `kb_chunks` + FTS5（trigram + 短查询兜底）+ 索引接口 | 纯关键词可检索 |
| M2 | 黄金集导入 + 评测脚本 + 首批基线数字 | **Recall@10 / MRR 基线** |
| M3 | 嵌入模型配置 + 向量召回 + RRF + 覆盖/阈值 | 混合检索，与 M2 对比 |
| M4 | 重排（可选）+ 前端检索测试与片段预览 | 可用界面 |
| M5 | 术语表/查询扩展 + 调优迭代 | 指标提升报告 |

M1–M2 不依赖任何外部服务，可先独立交付。

## 14. 验收标准

| 项 | 目标 |
|---|---|
| 切分质量 | 抽查 20 篇文档，无跨节碎片、表格完整、标题链正确 |
| 中文短查询 | 「支付」「窗格」等 2 字查询能命中 |
| 增量 | 修改一篇文档后只重建该文档片段，其余 chunk id 不变——**逻辑已实现，未写断言** |
| 评测可复现 | 同一 pipeline 两次运行指标完全一致 |
| 召回 | 黄金集 Recall@10 ≥ 0.85、MRR ≥ 0.6（首轮基线后确认） |
| 低置信 | 无答案问题不返回高分片段，前端有明确提示 |
| 性能 | 1 万片段下单次检索 P95 < 150ms（含向量）——**未压测** |

## 15. 风险

| 风险 | 对策 |
|---|---|
| 切分参数拍脑袋 | 每个参数都用黄金集 A/B，不凭直觉调 |
| 嵌入模型不可用/费用高 | 向量路可关闭，BM25 独立可用；失败自动降级 |
| 中文短词召回差 | LIKE 兜底 + 术语表；v2 可加 bigram 索引 |
| 表格解析丢失 | 飞书表格转 markdown 时保留表头；评测单列「表格」类用例 |
| 覆盖率低导致"召回不到" | 界面显式展示未索引清单；PDF 等类型标注不支持 |

**列表口径修正（2026-10-28）**：知识库列表原先只列 `kb_state != off` 的文档，同步完新文档后列表是空的，造成「知识库没同步到」的误解。现在改为列出项目下**所有已同步文档**：未收录的显示「未收录」徽标 + 关闭态开关，点一下即收录并建索引；筛选改为 全部 / 已收录 / 未收录 / 需处理；覆盖率改按「已索引 ÷ 所有已同步文档」计算，未收录会真实拉低覆盖率。批量入口「收录全部（N）」仅在存在未收录文档时出现。

### 17.6 扩语料到 28 篇后的复测（2026-10-28）

语料：28 篇会议纪要/转录全部收录并索引，**537 个片段**；黄金集扩到 **33 条**（新增 13 条覆盖另外 6 篇文档 + 1 条无答案）。

| 指标 | 旧（2 篇） | 扩语料后（28 篇） |
|---|---|---|
| 片段 Recall@5 | 0.947 | **0.903** |
| 片段 Recall@10 | 0.947 | **0.968** |
| 片段 MRR | 0.754 | **0.745** |
| 文档 Recall@10 | 1.000 | 1.000 |
| 无答案误召回 | 0.000 | 0.000 |

扩语料后 R@5 下降（0.947→0.895）是预期内的：候选变多、同义段落互相竞争。本轮据此做了三项调整：

1. **LIKE 兜底过滤停用词**：单字（是/的）与疑问虚词（什么/怎么/哪些）命中率过高，会挤掉真正相关的片段。过滤后 `ADE 是什么` 的噪声明显减少。
2. **术语表生效**：配置 `ADE=数字员工`、`OPC=一人公司` 后，`ADE 是什么` 恢复命中，片段 R@5 由 0.895 回到 0.947、MRR 0.679→0.771。这是"术语不一致"这一类失败的标准解法，成本极低。
3. **低置信阈值 0.25 → 0.30**：`年会奖品是什么` 的探针覆盖率恰好 0.25，被误判为可信；调整后无答案误召回回到 0。

**仍然失败的一条**：`目标客户是哪类企业` → 期望命中「国央国企」段落。问法与原文没有共同 3 字窗口，属纯语义错配，关键词路径无解。**这条只能等向量检索**，已作为 M3 的对照用例保留。

> 注意：本轮我在这套配置里写入了上面两条术语（索引设置里可改可删），它们属于项目知识，换项目需各自维护。

### 17.7 嵌入模型切换的向量隔离（2026-10-28）

问题：`listChunksWithEmbeddings` 原先不区分 `embedding_model`，换模型后旧向量与新查询向量会被放在一起算余弦。不同模型的维度/空间不可比，而代码里用 `Math.min(len)` 掩盖了维度不一致，属于**静默错误**——换模型复测会得到看起来正常、实际无意义的分数。

修复：

- 检索只取 `embedding_model = 当前配置模型` 的向量；未配置模型时向量路直接跳过。
- `getChunkStats` 增加 `embeddedCurrent`（当前模型已向量化）与 `embeddingStale`（属于旧模型、待重嵌）。
- 状态接口返回这两个数；前端在配置了模型时显示「向量 N」，有旧模型残留时显示「待重嵌 N」。
- 切换模型后旧向量仍保留（不删），重建索引时按 `embedding IS NULL OR embedding_model != 当前模型` 重嵌，失败可回滚到旧模型继续用 BM25。

验证：构造 `old-model` 两条向量，切到 `new-model` 后 `listChunksWithEmbeddings` 返回 0 条、统计显示 `embeddedCurrent=0 / embeddingStale=2`；切回 `old-model` 恢复 2 条。

**嵌入接入实况（2026-10-28）**：配置 `BAAI/bge-m3`（硅基流动，1024 维）后重建，28 篇 537 个片段切分与索引均正常，但嵌入接口返回 **HTTP 402（account balance is insufficient）**，向量一条都没写入，指标停留在纯 BM25 基线（片段 R@5 0.903 / R@10 0.968 / MRR 0.745）。索引流程按设计未因此中断。

同时补了一个健壮性改动：嵌入接口失败后进入 **60 秒冷却**，冷却期内检索跳过向量路、索引跳过嵌入，避免每次查询都白等一个注定失败的请求。实测同一轮 33 条评测的失败请求从 11 次降到 1 次，评测耗时降到约 2 秒。

### 17.8 混合检索接入 bge-m3 后的对比（2026-10-28）

嵌入：`BAAI/bge-m3`（硅基流动，1024 维），537 个片段全部向量化，耗时 12 秒。同一套 33 条黄金集：

| 指标 | 纯 BM25 | 混合（最终参数） | 变化 |
|---|---|---|---|
| 片段 Recall@5 | 0.903 | **0.935** | +3.2pp |
| 片段 Recall@10 | 0.968 | 0.968 | — |
| 片段 MRR | 0.745 | **0.778** | +3.3pp |
| 文档 Recall@5 | 0.935 | **0.968** | +3.3pp |
| 无答案误召回 | 0 | 0 | — |

分类型片段 R@5：通用 0.905 → **0.952**，缩写 1.0 → 1.0，数字/短词持平。

**关键发现：这批语料上 bge-m3 的余弦分数几乎没有区分度。** 实测「公司食堂几点开门」（无答案）最高余弦 0.513，高于「灰度发布怎么做」（相关）的 0.524；相关与不相关的片段都挤在 0.45–0.65 区间。原因基本是会议转录的文体高度一致——同一批说话人、同样的话题词，嵌入向量被"风格"主导。

因此**等权融合会显著劣化**：等权 + 无门限时 R@5 从 0.903 掉到 0.871，无答案误召回直接到 100%。最终参数是靠矩阵实验定的：

| 配置 | R@5 | R@10 | MRR | 无答案误召回 |
|---|---|---|---|---|
| 等权，无门限 | 0.903 | 0.968 | 0.719 | **1.000** |
| 等权，cos ≥ 0.55 | 0.839 | 0.935 | 0.820 | 0 |
| 权重 0.5，cos ≥ 0.55 | 0.871 | 0.935 | 0.787 | 0 |
| **权重 0.35，cos ≥ 0.60** | **0.935** | 0.968 | 0.778 | 0 |
| 纯 BM25 | 0.903 | 0.968 | 0.745 | 0 |

结论：**向量在这批语料里只能当低权重的补充，且必须过 0.6 的余弦门限**。参数做成可配置（`KB_WEIGHT_BM25 / KB_WEIGHT_LIKE / KB_WEIGHT_VECTOR / KB_MIN_COSINE / KB_VECTOR_MODE`），换语料后应重跑矩阵而不是沿用。

**仍未解决**：`目标客户是哪类企业` → 期望「国央国企」，该查询最高余弦只有 0.539，在 0.6 门限下被丢弃。把门限降到 0 能救这条，但无答案误召回会立刻回到 100%。这属于「语义相关但嵌入分数不够突出」，下一步可试：对短查询做查询改写、或换更适合口语语料的嵌入模型。

### 17.9 图片支持（2026-10-28）

PDF 仍不支持（用户确认可接受），但**图片改为必须支持**。

| 场景 | 处理 |
|---|---|
| 飞书云空间里的图片文件（png/jpg/jpeg/webp/gif/bmp） | `drive/v1/medias/:token/download` 下载 → 视觉模型转写 → 文本入库 |
| 飞书文档（docx）内嵌图片 | blocks 里的 image 块在转 markdown 时标记 token，转写后把占位替换为「（图片文字）…」 |

实现要点：

- 复用已有嵌入配置的 baseUrl 与 Key，新增配置项 `kb_vision_model`（索引设置里的「图片转写」），默认 `Qwen/Qwen3-VL-8B-Instruct`（硅基流动实测 7 秒/张，截图 UI 文字转写质量可用）。
- 未配置视觉模型时：图片收录直接失败并给出可操作提示；文档内嵌图片退化为「（图片）」占位，不影响正文入库。
- 单篇最多转写 20 张，超出或单张失败都退化为「（图片）」，不让一张图拖垮整篇。
- 实测：截图 `docs/screenshots/30-wf-running.png` 转写 7.3 秒，输出可读的中文界面文字；marker 替换单测通过（成功→「图片文字」、失败/超限→「（图片）」）。
- **未验证**：飞书图片 token 的真实下载链路（本机没有可用的图片文件）；带大量图片的文档的耗时。

### 17.10 M4 重排（2026-10-28）

两种实现并存：

- **专用重排模型**（默认）：配置项 `kb_rerank_model = BAAI/bge-reranker-v2-m3`，走硅基流动 `/v1/rerank`，返回 `relevance_score`。
- **对话模型打分**：模型名不含 `reranker` 时走 `/chat/completions` 让模型输出 JSON 分数，仅作没有专用模型时的兜底。

模型未配置、超时（20s）或返回异常时自动回退融合顺序。检索测试弹窗里可临时开关，接口参数 `rerank: true`。

同一套 33 条黄金集（片段级）：

| 流水线 | R@5 | R@10 | MRR | 无答案误召回 | 单次耗时 |
|---|---|---|---|---|---|
| bm25 | 0.903 | 0.968 | 0.745 | 0 | ~10ms |
| hybrid | 0.935 | 0.968 | 0.778 | 0 | ~400ms |
| **hybrid + bge-reranker** | **0.935** | 0.968 | **0.828** | 0 | **~0.69s** |
| hybrid + 对话模型打分（Qwen2.5-7B） | 0.903 | 0.968 | 0.817 | 0 | ~6.9s |

结论：

1. **专用重排明显优于对话打分**——快 10 倍、MRR 高 1.1pp、且 R@5 不再回落到 bm25 水平。
2. 重排仍然只提升首屏排序（MRR +5pp），不提升召回率；`目标客户是哪类企业` 的正确答案不在融合候选里，重排前后都缺失。
3. 因此定位为**默认关闭、可在检索测试里临时打开**；会话链路不接重排（每轮多 0.7s 不划算）。

### 17.11 会话内「使用知识库」开关（2026-10-28）

需求：会话输入框旁加勾选，勾上后本轮先检索项目知识库，把命中片段作为上下文交给 Agent。

落地：

| 层 | 内容 |
|---|---|
| 数据 | `turns.use_knowledge`（0/1，`ensureColumn` 自动补列），随 turn 落库 |
| 接口 | `POST /sessions/:id/turns` 新增 `useKnowledge` 字段 |
| 执行 | `runner.startTurn` 在启动 CLI 前调用 `kb.search(projectId, content, { topK: 6 })`；命中则把片段拼在提示词前（每段截断 600 字，附文档标题与小节路径），并追加「不足时请说明，不要编造」的约束；未命中则原样发送 |
| 可见性 | 检索结果作为 `kb_search` 事件写入事件流，Agent CLI 面板显示「知识库检索：命中 N 条」及文档列表 |
| 界面 | 输入框左侧「＋」图标按钮（22×22），点开为向上弹出的菜单，内含「知识库」开关行（开启时按钮变浅蓝，菜单内为拨动开关）；点击菜单外部关闭；状态按组件保存、不持久化 |

提示词结构：

```

如果这些内容不足以回答问题，请明确说明缺少什么，不要编造。

[1] 《文档标题》 · 小节路径

...

<原始输入>
```

实测（临时库，3 个片段）：在「＋」菜单里打开知识库开关 → 发送「灰度发布怎么做」→ CLI 面板出现「知识库检索：命中 3 条 1.《灰度手册》 › 灰度步骤 …」→ 随后正常进入 dsh 执行（该测试库没有 API Key，按预期在 LLM 调用处报错，说明提示词已传入）。

说明与限制：

- 重排不参与这条链路（默认关闭）；单次检索开销 ~0.4s（混合检索）。
- 勾选状态不持久化，刷新页面回到关闭；如需「按会话记住」需再加会话级字段。
- 检索到的片段会进入模型上下文，长文档命中 6 段最多约 3.6k 字，注意上下文预算。

### 17.12 超长代码块切分丢围栏（已修，2026-10-28）

实测：一个约 3.8k 字符的 js 代码块被切成 5 段，只有首段带开围栏、末段带闭围栏，中间 3 段是裸代码——作为 markdown 展示时会退化成普通文本，也让检索到的片段难以判断语言。

修复：`splitBlocks` 把围栏块标记为 `kind='code'`；`splitOversized` 对代码块按行切分，**每段都补上开围栏（含语言）与闭围栏**。修复后同一例子切成 4 段，每段围栏数均为 2。

注：本次修复只影响「超过 800 字符的代码块」，已索引的会议转录语料不含此类内容，无需重建；结构化的技术文档在下次收录/重建时会自动采用新切分。

## 19. 升级路径：Postgres + pgvector + Redis

> 定位：**不是现在要做，而是明确"什么时候必须做、要改什么、怎么回滚"**。当前单机 SQLite 方案在 10 万片段以内完全够用。

### 19.1 何时触发升级

满足任意一条即应评估：

1. 单项目片段数 **> 10 万**，进程内暴力向量检索超过 150ms；
2. 需要**多实例部署**（SQLite 是单写者，进程内 `EventEmitter` 总线无法跨实例广播）；
3. 需要把索引 worker 从 API 服务里拆出来独立扩缩容；
4. 需要可靠的定时任务 / 延迟任务（如「同步后 5 分钟自动重建」），进程内 `setInterval` 撑不住重启；
5. 需要跨进程事务（例如「发布文档 + 更新索引状态」原子化）。

### 19.2 目标架构

```
API 服务（N 实例，无状态）
   │  → Postgres（业务数据 + 向量 + 全文）
   │  → Redis（队列 + SSE 广播 + 缓存）

Worker 进程（M 实例）
   │  ← BullMQ 取任务：ingest / index / embed / reindex
   │  → Postgres 写片段与向量
```

- **Redis 不是给 pgvector 用的**，它服务于三件事：任务队列（BullMQ）、跨实例 SSE 广播（替代现在的 `bus`）、热数据缓存。如果只解决向量规模，Postgres 单独就够。
- 现在的进程内 `indexing` Set、`running` Map、`bus` 全部由 Redis + Postgres 承担。

### 19.3 数据模型映射

| 现在（SQLite） | 升级后（Postgres） |
|---|---|
| `kb_chunks`（embedding BLOB） | `kb_chunks(embedding vector(1024))` + `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)` |
| `kb_chunks_fts`（FTS5 trigram） | `tsv tsvector` + GIN 索引；中文需 `zhparser` / `pg_jieba`，或用 `pg_trgm` 的 trigram 近似（与当前行为最接近，迁移风险最小） |
| `kb_index_runs` | 保留为审计表；实时状态交给 BullMQ job state |
| `kb_eval_sets / kb_eval_runs` | 顺带补齐（见 B5） |
| `turns / events / sessions` | 原样迁移，`events` 改分区表（按月份） |
| `secrets.json` | 仍留在应用侧或 KMS，不入库 |

### 19.4 检索改造点

| 环节 | 现在 | 升级后 |
|---|---|---|
| 关键词 | FTS5 `MATCH` + `bm25()` | `tsv @@ websearch_to_tsquery` + `ts_rank_cd`，或 `similarity()`（pg_trgm） |
| 短词兜底 | `content LIKE '%q%'` | `content ILIKE` + trigram GIN，性能更好 |
| 向量 | 进程内 Float32 点积 | `ORDER BY embedding <=> $1 LIMIT 40` |
| 融合 | 应用层 RRF | 仍放应用层（SQL 里做 RRF 可读性差，收益有限） |
| 重排 | 外部 rerank API | 不变 |
| 阈值 / 权重 | 环境变量 | 不变（建议迁到配置表，按项目维度） |

**不改变的**：切分器、查询构造规则、黄金集、`/kb/*` 接口契约、前端。升级对上层是透明的。

### 19.5 迁移步骤（可回滚）

1. **影子索引**：新管道双写 Postgres，SQLite 继续服务线上；同一份黄金集分别跑两套检索，对比 Recall/MRR（预期无差异，差异即迁移 bug）。
2. **灰度读**：按项目维度切读（配置开关），先切 1 个项目观察一周。
3. **切写**：停掉 SQLite 写入，Postgres 成为唯一真相源；SQLite 保留只读快照一周。
4. **回滚**：任一阶段异常，把读开关切回 SQLite + 恢复写入即可；因为片段与向量都能由正文快照重建，回滚代价是重跑一次索引（约 12 秒 / 537 片段）。

### 19.6 资源规格

| 规模 | Postgres(+pgvector) | Redis | Worker | 合计建议 |
|---|---|---|---|---|
| ≤ 1 万片段，<10 QPS | 1 vCPU / 1 GB | 128 MB | 与 API 同机 | 2 vCPU / 2 GB |
| 10 万片段，几十 QPS | 2 vCPU / 2 GB（HNSW 常驻 ~1 GB） | 256 MB | 1 vCPU / 512 MB | 4 vCPU / 4 GB |
| 百万片段 | 4–8 vCPU / 8–16 GB | 1 GB | 2 vCPU / 1–2 GB | 独立三台 |

磁盘按语料的 2–3 倍估（数据 + WAL + 索引 + 备份）。向量内存估算：`片段数 × 维度 × 4 字节 × 1.5`（HNSW 索引）。

### 19.7 升级前必须补的功课

1. **黄金集要跨语料**：现在的 33 条来自同一批会议录音，迁移对比前至少补 20 条来自结构化文档的用例，否则"两套检索都 0.9"不能说明没退化。
2. **中文分词选型**：`zhparser` 需要装扩展和词典，`pg_trgm` 行为更接近现在的 trigram 但索引更大。建议先 `pg_trgm`（迁移风险最低），文本质量不够再换 `pg_jieba`。
3. **观测**：迁移前把检索耗时、命中数、低置信比例打成指标（Prometheus 或简单日志聚合），否则无法判断灰度期间是否退化。
4. **备份与恢复演练**：Postgres 的 PITR 要真跑一次恢复，不能只看文档。

### 19.8 结论

- **现在不升级**：537 片段、单机、单用户场景，SQLite + 进程内检索是最优解，多一套 PG + Redis 只增加运维面。
- **触发信号出现时**：按 §19.5 做影子索引 + 灰度读，切只影响存储层，切分与评测体系全部复用。
- **最先需要 Redis 的场景**：多实例部署（SSE 广播）和异步任务持久化；这两项比"向量规模"更早到来。
