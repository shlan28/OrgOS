# 「项目中心 - 代码审查」技术方案（双审交叉验证）

> 创建日期：2026-09-04
> 更新日期：2026-09-05（v3：新建/编辑检查项与强化检查项弹窗样式规范化——控件统一 field-input/field-select/field-textarea 全宽样式 + 代码字段等宽浅灰底语义样式；v2：人工复审生产端落地为 A' 形态——GitLab 原生复审 + webhook 准实时同步 + MR 状态机扩展 + 复审工作台跳转入口）

## 1. 背景与目标

项目详情页现有 9 个导航项，本期新增第 10 个「代码审查」（Code Review）。核心诉求两个：

1. **有代码审查的规则**——审查不是随缘看代码，而是有明确依据的检查标准；
2. **能检验代码审核的质量**——审查本身准不准，要有可度量的验证机制，而非只看产出报表。

**方案选型**：已确认采用「双审交叉验证」方案（此前三方案对比中的方案二），人工复审生产端落地为 **A' 形态**：

- 每个合并请求（MR）由两条独立审查线各出意见：**ADE 初审**（机器线）+ **人工复审**（成员线）；
- **ADE 初审意见只存 Loom，不下发 GitLab**——GitLab MR 页上看不到任何 ADE 意见，双盲靠「隔离下发」成立；
- **人在 GitLab MR 页原生复审**（完整 diff + 行级评论），评论通过 **note webhook 准实时同步**回 Loom（秒级，1~3s），定时轮询对账兜底（生产形态）；
- 系统对两条线的意见做**交叉比对**，比对结果分三类：双方一致 / 仅 ADE 提出 / 仅人工提出；
- 对「仅 ADE 提出」的意见由人工**裁决**（有效 / 误报）；「仅人工提出」即 ADE **漏检**；
- 由此得出可计算的质量指标：**一致率、ADE 误报率、ADE 漏检数**——检验质量内建于流程，不是事后编造的报表；
- 漏检意见可**反哺审查标准**（一键生成检查项建议），形成「审查 → 比对 → 裁决 → 强化标准」闭环。

两个需求的咬合关系：**规则（检查项）是两条审查线的共同依据，每条意见必须挂载检查项**，因此规则在每次审查中被强制消费，而一致率/误报/漏检均可按检查项归因。

与其他 tab 的职责边界（延续「每个 tab 只回答一个问题」原则）：

| 模块 | 回答的问题 |
|---|---|
| 代码 | 项目有哪些仓库 |
| **代码审查** | **MR 审得怎么样、审查本身准不准** |
| 安全审查 | 扫出了什么安全问题（漏洞视角，与本期无结构复用关系） |
| 测试 | 质量防线覆盖与通过情况 |

本期范围：

- **不参考/不复用安全审查的规则引擎形态**（关键词/正则匹配 + 扫描记录），检查项是「供人阅读与勾对的审查标准」，非机器匹配规则；
- 做完整双审闭环：检查项管理 + MR 审查队列（双栏对比 + 裁决）+ 一致性报告（KPI + 漏检反哺），不分期；
- 纯前端 Mock，不接 GitLab 真实数据；写操作仅本地 state 生效。

约束与前提：

- 视觉与交互完全遵循现有体系：浅色 macOS 风、Settings 式分组卡片 + 行式布局、CSS 变量、无第三方 UI/图表库；
- 数据挂 `Project`（与 `repos` / `security` 同级），写操作统一走 `onUpdateProject`；
- 当前登录用户沿用全局设定 **shilu**（人工复审动作以其名义执行）。

## 3. 总体设计

### 3.1 信息架构（面板内自上而下）

```

│

│
├── ① 段一：审查队列（工作台主线，默认段）
│   ├── Section「合并请求（N）」

│
└── ③ 段三：一致性报告（需求 2：检验）

    ├── Section「漏检清单（N）」
    │     行 = 「仅人工提出」的意见汇总：MR 标题 + 检查项 + 文件:行号（mono）+ 问题摘要
    │           右侧 = [强化该检查项] 文字按钮 → 打开新建检查项弹窗（预填分类，闭环反哺）

    │     按检查项统计漏检 / 误报 / 一致次数，降序；漏检 ≥ 1 的排最前

```

### 3.2 MR 状态机与流转机制（v2 新增）

MR 生命周期扩展为四阶段（原「待复审」拆分）：

```
① ADE 初审中 ──自动──→ ② 待人工复审 ──人工在 GitLab 提交评论──→ ③ 待裁决 ──裁决+结论──→ ④ 已完成
 (adeReviewing)         (humanReviewing)    (webhook 同步 + 比对)        (resolved)
```

| 阶段 | 进入条件 | 离开条件 | 面板表现 |
|---|---|---|---|
| ① ADE 初审中 | MR 提交（GitLab webhook 创建队列项） | ADE 初审完成（自动） | 行徽标 info「初审中」；点开为**初审占位视图**（进度提示，无意见） |
| ② 待人工复审 | ADE 初审完成 | 收到该 MR 的人工评论（note webhook） | 行徽标 warning「待复审」；点开为**复审工作台**（「人工复审 ↗」跳 GitLab + ADE 意见已就位但**不出示**） |
| ③ 待裁决 | 首条人工评论同步到达 → 自动比对 | 全部裁决 + 出结论 | 现有双栏对比视图（本次已实现） |
| ④ 已完成 | 通过 / 打回 | — | 只读回看（本次已实现） |

**流转触发机制（生产形态）**：

- ① → ②：ADE 初审为异步任务，完成后自动流转 + 通知复审人；
- ② → ③：**note webhook 准实时同步**——人在 GitLab MR 页提评论，1~3 秒内到达 Loom，首条评论到达即触发交叉比对并自动切到裁决态；后续评论持续追加（编辑/删除同步联动）；
- 兜底：每 10~15 分钟增量轮询对账 + 每日全量对账（webhook 丢包补拉）；
- **双盲保障**：ADE 意见永不下发 GitLab（MR 页上不存在），复审人在 GitLab 上只能看到代码 diff，交叉验证不受锚定污染。

**双盲时序说明**：② 阶段面板不出示 ADE 意见（复审人跳 GitLab 审，天然看不到）；评论同步回来进入 ③ 后双栏才同时可见——时序上人工意见的产生先于 ADE 意见的可见，隔离成立。

### 3.3 MR 审查详情（二级视图，核心交互）

**② 待人工复审：复审工作台视图（v2 新增）**

```
← 返回审查队列

feat: 购物车满减促销计算                        [待复审]
luyu · cart-discount → dev · +286 −42 · 9 文件 · 09-03 16:40

┌──────────────────────────────────────────────┐
│  ⏳ ADE 初审已完成（3 条意见）· 等待人工复审      │
│                                              │
│  复审在 GitLab MR 页进行：                     │
│  1. 点击下方按钮跳转到 MR                      │
│  2. 在 diff 上行级评论提出意见                  │
│  3. 评论将准实时同步回来，自动比对双方意见        │
│                                              │
│  [人工复审 ↗]   ← 跳转 GitLab MR（新窗口）      │
└──────────────────────────────────────────────┘
（同步状态行：webhook 正常 · 上次同步 09-04 10:18）
```

- **[人工复审 ↗] 主按钮**（黑底，同 btn-primary）：`window.open(mrUrl, '_blank')` 跳转 GitLab MR 页；卡片下方常驻同步状态小字；
- **ADE 意见隐藏但计数可见**：展示「ADE 初审已完成（N 条意见）」——计数透明给进度感，内容隔离保双盲；
- **Mock 模拟同步**：点击「人工复审 ↗」后，Mock 视为「复审人已在 GitLab 提交评论」——约 2s 后（模拟 webhook 到达）预置的人工意见 + 比对结果就位，MR 自动流转到 ③ 待裁决态，视图切换为双栏对比，顶部出现「评论已同步 · 已自动比对」过渡提示条（3s 自动消失）；
- **① ADE 初审中视图**：居中进度占位（ADE 头像 + 「初审进行中 · 预计 1 分钟内完成」），Mock 中不预置该状态，仅作为状态机的完整定义（新 MR 由真实接入时产生）。

**③ 待裁决 / ④ 已完成：双栏对比视图（本次已实现，小调整）**

```
← 返回审查队列

feat: 购物车满减促销计算                  [待裁决]
luyu · cart-discount → dev · +286 −42 · 9 文件 · 09-03 16:40
ADE 初审于 09-03 16:41 · 人工复审同步于 09-04 10:20 · 依据启用中的 9 条检查项

┌──────────────────────┬──────────────────────┐
│ ADE 初审（4 条）        │ 人工复审（3 条）        │
├──────────────────────┼──────────────────────┤
│ ┃[双方一致] 满减边界…    │ ┃[双方一致] 满减边界…   │
│ ┃[仅 ADE] 嵌套过深…     │ ┃[仅 ADE · 待裁决]…    │ ← 裁决位
│ ┃   [有效] [误报]       │ ┃[ADE 漏检] 循环内…   │
│ ┃…                     │ ┃…                   │
└──────────────────────┴──────────────────────┘

裁决进度 2/2 · 全部裁决后可出结论

[人工复审 ↗]  [打回 MR]              [确认通过]
```

- 双栏对比布局、意见卡片、裁决交互、结论动作均沿用已实现形态；
- **底部常驻 [人工复审 ↗] 描边小按钮**（裁决区左侧）：随时跳回 GitLab MR 页补充评论（真实系统：新评论继续 webhook 同步追加；Mock：仅跳转动作，不追加意见）；
- 头部信息行增加「人工复审同步于 …」时间（= ② → ③ 流转时刻，来自 webhook）；
- **已完成 MR**：只读回看——裁决按钮消失（显示结论徽标），底部显示 `结论：通过 · 09-04 15:10`（打回同理），无操作按钮（保留 [人工复审 ↗] 跳转）。

### 3.4 核心交互流（v2 更新）

```
检查项配置（段二）              MR 审查（段一）                        质量检验（段三）
─────────────────            ─────────────────                    ─────────────────
预置检查项 启停 ──┐            MR 进入队列（Mock 预置）                 KPI 聚合（已完成 MR）
自定义检查项 增改 ─┴→ 启用集 → ADE 初审意见（挂检查项）                     │
                              + 人工复审意见（挂检查项）        一致率 = 双方一致 / 意见总数
                                    │                          误报率 = 误报 / ADE 意见数
                                    ▼                          漏检数 = 仅人工提出
                             双栏对比 + 逐条裁决 ─────────→ 裁决完成 → MR 已完成
                                    │                                    │
                                    ▼                                    ▼
                              结论：通过 / 打回                    漏检清单 → [强化该检查项]
                                                                    → 新建检查项（预填）→ 回到段二
```

- **交叉比对为 Mock 预置**：`ReviewComment.match` 字段在数据中直接标定（双方一致 / 仅 ADE / 仅人工），语义 = 相同 `file + line + itemId` 的两条意见为一致；不在前端做实时 diff；
- **裁决与指标联动**：所有指标由聚合函数从已完成 MR 现算。用户裁决一个待复审 MR 后切到报告段，KPI 与漏检清单即时变化——「检验质量」随流程真实推进；
- **反哺闭环**：漏检清单的 `[强化该检查项]` 打开新建弹窗，预填分类与说明（标题占位如「强化：循环内 IO」），确认后新检查项进入审查标准段并默认启用。

## 4. 页面设计

### 4.1 顶部分段切换 + 说明

- `SegmentedControl` 三段：**审查队列（N）** / **审查标准（M）** / **一致性报告**（N = MR 数，M = 启用检查项数；默认落在审查队列段）；
- 段下方灰色小字说明（同 `SEG_HINT` 模式）：
  - 队列段：「每个 MR 由 ADE 初审 + 人工复审双线独立审查，交叉比对后由人工裁决」
  - 标准段：「检查项是两条审查线的共同依据，每条意见必须挂载检查项」
  - 报告段：「从已完成审查的裁决结果中聚合一致率、误报与漏检」

### 4.2 段一：审查队列

#### MR 列表（Section「合并请求（N）」）

- 每行（`Row` + 点击进二级视图）：
  - 左：MR 标题（13.5px 主，如 `feat: 购物车满减促销计算`）+ 作者（`luyu` 12px 灰，前置 · 分隔）；
  - 次级：`cart-discount → dev · +286 −42 · 9 个文件 · 09-03 16:40`（增删行数分别绿/红着色，其余灰）；
  - 右：状态徽标（待复审 = warning / 已完成 = neutral）+ 结论徽标（已完成时：通过 = success / 打回 = danger）+ 展开箭头 ⌄；
- 排序：待复审在前（按时间倒序），已完成在后（按时间倒序）；
- 空状态：居中空状态——检查单线框图标 + 「暂无审查请求」+「MR 提交后将自动进入审查队列」。

#### MR 审查详情（二级视图）

- 顶部返回按钮「← 返回审查队列」（同知识库二级页）；
- 头部区：MR 标题（15px 加粗）+ 状态徽标 + 结论徽标；次级信息两行：
  - `luyu · cart-discount → dev · +286 −42 · 9 个文件 · 09-03 16:40`；

- **双栏对比区**（核心）：`grid-template-columns: 1fr 1fr`，窄容器（< 640px）降级单列堆叠；
  - 栏头：`ADE 初审（4 条）` / `人工复审（3 条）`（12.5px 灰，计数实时）+ 左栏机器人图标 / 右栏当前用户 shilu 名字；
  - 意见卡片（两栏同构）：

### 5.4 交叉比对口径（Mock 语义）

- 一致 = 两条意见（一 ADE 一人工）`file + line + itemId` 相同，Mock 中双方各预置一条并同标 `match: '双方一致'`；
- `totalPairs`（比对单元）= 双方一致对数 + 仅 ADE 条数 + 仅人工条数——**一致率分母按比对单元计**，避免一致意见被双计稀释；
- 误报率分母 = 已裁决的仅 ADE 意见（未裁决不计入，鼓励裁决完再看报告）；
- 待复审 / 待裁决 MR 均不计入报告聚合；出结论（已完成）后自动并入。

## 10. 风险与说明（v2 更新）

- Mock 的 webhook 同步为「点击跳转 → 2s 就位」的确定性模拟，不体现真实事件流；接入真实系统时由后端 note webhook 驱动（秒级）+ 定时对账兜底，面板结构不变；
- 复审工作台「ADE 意见计数可见、内容隔离」是双盲与进度感的折中——若严格双盲要求连计数也不可见，可降级为「ADE 初审已完成」纯文案（预留一处文案改动即可）；
- 人工意见在 GitLab 上是自由文本，真实系统需评论归因（`#检查项` 约定或裁决时补挂）——Mock 意见为结构化预置，不体现归因过程；
- merge 竞态（人在 GitLab 直接合并）为生产形态风险，Mock 不模拟；接入时需收 merged webhook 标记「未经裁决合并」并告警；
- 其余沿用 v1：一致率按比对单元口径（KPI 次级文案展示分子分母）、误报率仅统计已裁决、裁决撤销仅意见级、双栏窄容器降级单列。
