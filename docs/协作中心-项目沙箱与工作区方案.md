# 协作中心 · 项目沙箱与工作区方案

> 日期：2026-10-25
> 状态：设计稿，待评审
> 关联：[协作中心-会话团队协作改造方案.md](协作中心-会话团队协作改造方案.md)（P1 工作区隔离的展开）

## 1. 背景与目标

当前 agent 在固定的 `workdir` 里执行，每个 turn 一个 dsh 进程。多个会话并行时共享同一工作目录，会出现文件互相覆盖、git 冲突、测试/端口互相干扰。

本方案定义：

- 项目级**沙箱**（持久工作区 + 资源隔离）
- 会话级**工作目录**（临时、可合并）
- 终端 tab、代码同步、提交与合并、非 git / 非研发项目的降级策略
- 本地 Docker 与云端部署的对应关系

目标：团队可以安全地在同一项目上并行/串行执行会话，同时控制 CPU、内存、网络与磁盘成本。

## 2. 核心决策

| 决策 | 结论 |
|---|---|
| 项目类型 | **新建项目时必选**「研发项目 / 非研发项目」，创建后不可修改（如需变更走迁移流程） |
| 非研发项目 | 不显示「代码」「终端」tab，不创建沙箱卷与容器，`workspaceMode = none` |
| 会话模式 | 默认 `chat`；**唯一升级方式**：检测到代码操作后用户确认 → `code`；不支持随意切换，`code` 不回退 |
| 工作区模式 | `none` / `serial` / `worktree`，默认按项目能力自动选择 |
| 沙箱粒度 | **一个项目一个持久沙箱卷**；仓库只克隆一次 |
| 执行容器 | 推荐**每会话一个容器**，仅 `code` 模式会话启动，挂载项目卷与会话目录（资源限制按会话） |
| Docker 启动时机 | **按需启动**：纯问答会话不启动项目容器；只有代码会话、打开终端或首次代码操作时才启动，空闲后停止、卷保留 |
| 并发控制 | 同一会话串行；同一项目默认串行，worktree 模式可并行 |
| 代码来源 | 云端仓库；沙箱内 `fetch` + 会话分支，不重复 clone |
| 提交方式 | 会话分支 → 提交 → push → MR（团队默认）；本地直接合并为可选 |
| 终端 | 格 4 新增「终端」tab（仅研发项目），接入项目沙箱容器 |
| 非研发项目 | 不复制工作区，只读上下文 + `artifacts/<sessionId>/` 输出 |
| 非 git 研发项目 | 默认 `serial`；可选快照副本；不自动 `git init` |

## 3. 项目类型与工作区策略

### 3.1 项目类型

新建项目弹窗新增必选项「项目类型」，默认选中「研发项目」：

| | 研发项目 | 非研发项目 |
|---|---|---|
| 典型场景 | 有代码仓库、需要改代码/测试/提交 | 文档、运营、数据分析、方案整理 |
| 「代码」tab | 显示 | **隐藏** |
| 「终端」tab | 显示（默认收起） | **隐藏** |
| 沙箱卷 / Docker | 需要 | **不需要** |
| 仓库配置 | 需要 | 不涉及 |
| 工作区模式 | `worktree`（git）或 `serial`（非 git） | 固定 `none` |
| Agent 产出 | 代码、测试报告 | `artifacts/<sessionId>/` 或项目文档/知识库 |

约束：

- 项目类型**创建后不可修改**（避免已有会话、仓库、沙箱状态不一致）；确需变更走单独迁移流程
- 非研发项目不创建沙箱卷、不启动任何容器，项目详情页也不注册「代码 / 终端」tab
- 研发项目创建后可以没有仓库（`serial` 模式），后续在「代码」tab 添加

### 3.2 workspaceMode

| 模式 | 适用 | 是否复制代码 | 并行 | 合并方式 |
|---|---|---|---|---|
| `none` | 非研发项目 | 否 | 可并行（各写各的产出目录） | 无需合并 |
| `serial` | 非 git 研发项目 / 暂不需要并行的项目 | 共享一份工作区 | 否（项目级队列） | 无需合并 |
| `worktree` | git 研发项目 + 需要并行 | 每个活跃会话一份工作区（共享 `.git`） | 是 | 会话分支 + MR |

默认规则：

1. 研发 + git 仓库 → `worktree`（可配置为 `serial`）
2. 研发 + 无 git → `serial`
3. 非研发 → `none`

项目可在设置中覆盖默认值。

## 4. 目录设计

### 4.1 项目沙箱卷

```
<sandboxRoot>/<projectId>/
├── repos/                            # 仓库主克隆（共享 .git，只克隆一次）
│   ├── loomweb/
│   └── pay-gateway/
├── worktrees/                        # 会话工作目录（临时）
│   └── <sessionId>/
│       ├── loomweb/                  # git worktree，分支 session/<id>
│       └── pay-gateway/
├── artifacts/<sessionId>/            # 测试报告、构建产物、导出文件
├── logs/<sessionId>.log              # 终端与执行日志
├── home/                             # 共享缓存（.npm、.cache）
└── meta.json                         # 仓库列表、基准分支、资源限制、创建时间
```

容器内固定映射：

```
/workspace    ← worktrees/<sessionId>（或 repos/ 下的工作区）
/cache        ← home/
/artifacts    ← artifacts/<sessionId>
/tmp          ← tmpfs
```

### 4.2 沙箱根目录放哪里

不要在项目仓库、`src/`、`node_modules/` 或 Code tab 的仓库目录内。

| 环境 | 建议路径 |
|---|---|
| 本地开发 | `ORG_OS_SANDBOX_DIR`，默认 `server/data/sandboxes`（gitignore、备份排除） |
| 桌面/生产（macOS） | `~/Library/Application Support/Org-OS/sandboxes` |
| 桌面/生产（Linux） | `~/.local/share/org-os/sandboxes` |
| 云端 | 项目持久卷（PVC / EFS / 本地 NVMe），如 `/var/lib/org-os/sandboxes/<projectId>` |

不要挂载宿主项目目录、`~/.ssh`、Docker socket。

## 5. 会话工作目录

### 5.1 worktree 为什么不重复拉代码

`git worktree` 共享同一份 `.git` 对象库：

- 不重新 clone / fetch，不复制历史
- 每个 worktree 只多一份**检出文件**、index、HEAD
- 真正占空间的是每个活跃会话的 `node_modules`、构建产物，而不是 git 历史

示例：1 GB 历史 + 200 MB 工作区，一个 worktree 约多 200 MB；10 个并发活跃会话 ≈ 2 GB 工作区 + 1 GB 共享对象库。

### 5.2 会话目录生命周期

1. 会话开始：`fetch origin` → 基于最新默认分支创建 `session/<id>` → `worktree add`
2. 执行：容器挂载该会话目录，agent 在此工作
3. 提交 / 推送 / 创建 MR 由用户在改动栏触发；合并或放弃后再 `worktree remove` + 删除分支
4. 会话保留期内的 `artifacts/`、`logs/` 可继续访问

> 空闲或 turn 结束**不会自动提交或清理**：容器可以停，但会话与 worktree 仍保留，直到用户主动提交/推送或删除会话。

### 5.3 限制与清理

- 只为**活跃会话**创建 worktree；结束后清理，避免磁盘随会话数增长
- 可配置活跃会话上限与 LRU 回收
- `home/` 缓存可共享；并发会话建议各自 `home/<sessionId>/`，只软链共享 npm/pnpm 缓存
- 纯问答 / 只读会话不创建 worktree

### 5.4 会话模式：chat / code（仅确认式升级）

会话只有两种模式：

| 模式 | 工作目录 | 项目容器 | 适用 |
|---|---|---|---|
| `chat`（默认） | 不创建 worktree | 不启动 | 问答、方案讨论、文档整理、知识库查询 |
| `code` | 创建 worktree | 启动 | 读写代码、执行命令、构建、测试 |

**唯一的标记方式：确认式升级**

1. `chat` 会话中检测到代码操作（打开终端、shell/exec、写入/编辑文件、git、包管理、构建或测试命令）
2. 系统提示「检测到代码操作，是否开启代码模式？」
3. 用户确认 → 会话标记为 `code`，创建 worktree、启动容器，从**下一轮**开始生效
4. 用户拒绝 → 保持 `chat`，本会话不再重复提示

没有其他入口：新建会话时不能选模式，会话头部没有手动切换，打开终端也走同一个确认。

**不能随意切换**

- `chat → code` 只能通过上述确认发生
- `code → chat` 不支持：一旦会话进入代码模式就保持代码模式
- 如果之后只想纯问答，**新建一个会话**，不要复用代码会话
- 原因：worktree、容器、dsh cwd、已产生的代码改动都有各自的状态与清理周期，中途来回切换会让状态难以一致，也容易让用户误以为“切到问答就不会动代码”

**执行时机与限制**

- 模式切换只影响尚未开始的 turn；运行中的 turn 不会中断
- dsh 启动时确定 cwd，**无法在 turn 中途挂载仓库**；确认升级后当前轮按原模式结束，下一轮进入代码模式
- `chat` 会话不挂项目仓库，cwd 为临时目录或只读上下文；shell/写文件等工具由权限策略拒绝，检测到即触发提示
- 非研发项目固定 `chat`，没有升级入口

> 不引入会话生命周期：`idle` 只表示没有运行中的 turn；提交、推送、创建 MR 由输入框上方的改动栏触发，会话本身没有「完成 / 归档」状态。

## 6. 容器与资源限制

### 6.1 容器模型

- **项目级**：持久卷 + 仓库主克隆（纯数据，不常驻进程）
- **会话级**：只有 `code` 模式的会话才启动容器，挂载项目卷和会话目录；用完停止/回收
- `chat` 模式的会话不挂项目仓库，也不创建 worktree；本地可直接使用宿主 dsh，云端使用不挂项目卷的基础沙箱
- 长期共享容器只适合 `serial` 模式；要按会话限制资源，必须每会话一个容器

### 6.2 资源限制（Docker）

```
--cpus=2
--memory=4g --memory-swap=4g
--pids-limit=512
--network=<项目专用 bridge>         # 或 internal + 出口代理白名单
--read-only                         # 根文件系统只读
-v <sandbox>/<projectId>/worktrees/<sessionId>:/workspace
-v <sandbox>/<projectId>/home:/cache
-v <sandbox>/<projectId>/artifacts/<sessionId>:/artifacts
--tmpfs /tmp:size=512m
--user <uid>:<gid>                  # 避免宿主文件变成 root 所有
```

说明：

- 网络不能完全断：`git fetch` / 安装依赖需要可控出口（代理或白名单）
- 目录方案无法强制 CPU/内存/网络限制；macOS 上尤其需要容器/VM
- 磁盘配额单独配置（卷大小 / 定期清理）

### 6.3 凭证与安全

- 每个沙箱注入限定仓库、短期有效的 git token
- 不挂载 Docker socket、宿主 SSH、生产凭证
- 终端命令与执行日志落到 `logs/<sessionId>.log`，便于审计

### 6.4 Docker 的启动时机（按需启动）

**新建项目不启动容器；纯问答会话也不启动项目容器。**

这里要区分两层：

- **执行沙箱**：dsh 进程本身运行的地方。本地可以就是宿主进程；云端出于安全考虑，默认也应放在基础沙箱里（不挂项目仓库）
- **代码工作区容器**：挂载项目卷 / 会话 worktree 的容器。只有需要读写代码、执行构建/测试或打开终端时才启动

| 动作 | 项目工作区容器 |
|---|---|
| 新建研发项目 | **不启动**（后台只准备卷与仓库克隆） |
| 打开「代码」tab | **不启动**（只展示仓库与同步状态） |
| 纯问答 / 文档整理会话 | **不启动**，不创建 worktree |
| chat 会话中检测到代码操作 | 不启动；提示用户确认是否开启代码模式 |
| 用户确认开启代码模式 | 下一轮执行前创建 worktree、启动该会话容器 |
| 打开「终端」tab | 走同一个确认；确认后才启动容器 |
| 空闲 5–10 分钟 / 手动停止 | 停止容器，卷与依赖缓存保留 |
| 手动「停止沙箱」 | 立即停止 |
| 项目删除 | 停止并删除容器与卷 |

规则：

- 非研发项目：没有沙箱卷，也没有项目容器，任何操作都不会触发 Docker
- 研发项目的会话默认 `chat`；**唯一升级方式**是检测到代码操作后用户确认（详见 5.4）
- 用户拒绝升级：保持 `chat`，本会话不再重复提示；需要代码请新建会话
- 一旦进入 `code` 不再回退 `chat`
- dsh 在启动时确定 cwd，**无法在 turn 中途给运行中的容器追加仓库挂载**；确认升级后从下一轮生效
- 终端 tab 显示沙箱状态：`未创建 / 准备中 / 已停止 / 启动中 / 运行中 / 异常`，支持手动启动/停止/重试
- 容器停止不删除卷；下次启动是热启动
- 云端对应关系：`code` 会话进入 `running` 时调度挂载项目卷的 Pod；`chat` 会话只使用基础沙箱（或直接使用服务端运行时），不挂项目卷；空闲后删除 Pod，PVC 保留

**为什么不项目创建 / 会话开始就启动：**

- 纯问答、文档整理不需要代码，启动带仓库的容器纯属浪费
- 按需启动才能把 CPU/内存/网络限制落到真正使用代码的会话
- 启动失败可以在终端/会话界面明确提示并重试，而不是在创建项目或发第一条消息时报一个用户无法处理的错误

## 7. 终端 tab

- 仅**研发项目**注册「终端」tab；非研发项目不显示
- 位置：格 4（最后一个格子）的 `TAB_ITEMS` 新增「终端」，默认收起，可通过 ＋ 菜单打开
- 前端：xterm.js（`@xterm/xterm` + fit addon）
- 通信：WebSocket + PTY（`node-pty`），后端 `docker exec -it <sandbox-container> bash`
- 打开流程：校验项目成员 → `get-or-create` 项目沙箱 → 启动/复用会话容器 → 建立 PTY
- 权限：仅项目成员；终端操作写审计日志
- 终端关闭不销毁沙箱；容器空闲回收，卷保留
- 资源限制与容器一致（CPU / 内存 / 网络 / pids）

## 8. 代码同步、提交与合并

### 8.1 会话开始

```
fetch origin
→ 基于远端默认分支创建 session/<id>
→ worktree add（worktree 模式）
→ 安装/复用依赖
```

不要在脏工作区上继续改；上次残留未提交改动先清理或重置。

### 8.2 提交

- 提交、push、创建 MR 由用户通过输入框上方的改动栏触发，不依赖“会话结束”
- 删除会话前必须处理未提交改动与未推送提交（提示确认）；不要在 dirty worktree 上直接删除
- 提交信息可由 agent 生成，附会话标题/ID
- **不要直接提交 main**；每个会话一个分支，push 后走 MR

### 8.3 合并方式

| 方式 | 适用 | 说明 |
|---|---|---|
| MR / PR | 团队默认 | 评审 + CI + 审计；冲突在 MR 处理 |
| 本地 merge | 单人/小团队 | 共享 `.git`，主工作区 `git merge --no-ff session/<id>` |
| cherry-pick / patch | 只取部分改动 | 分支分叉较远或会话混有无关改动 |

要点：

- 合并前建议 `git rebase <base>` 更新分支
- 同一目标分支的合并串行执行
- 冲突在目标工作区解决，不在会话 worktree 解决
- 锁文件、生成物必须在 `.gitignore`，避免无意义冲突
- 合并/放弃后：`worktree remove` → `branch -d`，需要时保留一段时间供追溯

### 8.4 未提交改动栏（输入框上方）

在 ChatPane 输入框上方增加一行改动状态，只在 **`code` 会话 + 有可编辑仓库 + 存在未提交改动** 时显示：

```
+123 −45 · 3 个文件        [查看改动]  [提交]
```

- 多仓库项目按仓库聚合（`loomweb +80 −12 · pay-gateway +43 −33`），只统计 `editable` 仓库
- **hover**：浮层展示文件列表（`A/M/D`、每文件 +/−）；hover 单个文件显示**首个 diff 片段（限 10–20 行）**
  - 不直接在 tooltip 里渲染整份文件内容：大文件会卡、且 diff 可能包含敏感信息
  - 点击「查看改动」打开完整 diff 面板（按文件懒加载、可折叠、支持大文件/二进制元信息）
- **提交**：弹窗选择文件（默认全部）、预填 commit message、提交后栏变为
  `已提交 3 个文件 · 待推送   [推送并创建 MR]`
- **推送**：选择远端分支（默认 `session/<id>`）、目标分支、MR 标题；成功后展示 MR 链接
- 状态流转：`有未提交改动 → 已提交未推送 → 已推送 / 待 MR → 已合并 / 已放弃`
- 数据来源：`GET /api/sessions/:id/changes`（各仓库 `git status` + `diff --numstat` + 摘要；完整 diff 单独按文件取）
- 刷新时机：turn 结束、终端命令执行后、提交/推送后；可通过 SSE `workspace_dirty` 推送变更
- `chat` 会话与非研发项目不显示这一行
- 只读仓库不参与提交；若只读仓库出现改动（异常）只提示，不允许提交

## 9. 非 git 与非研发项目

### 9.1 非 git 研发项目

- 默认 `serial`：同一工作目录同时只跑一个会话，零冗余
- 需要并行时可选**快照副本**：`rsync` 复制（排除 `node_modules`、`dist`、缓存），结束用 `diff -ruN` / `patch` 合并
- 可提供「启用版本管理」入口：用户确认后 `git init`，或创建不污染项目目录的影子仓库
- **不自动给用户项目 `git init`**

### 9.2 非研发项目（`none`）

- 不复制工作区，agent 读取共享上下文（知识库、文档、规范）
- 产出统一写到 `artifacts/<sessionId>/`，或直接保存为项目文档/知识库条目
- 多个会话各写各的目录，可并行
- 如果确实要改共享文档，再退化为 `serial`

## 10. 会话内容与产物存储

### 10.1 当前实现

| 内容 | 存储 |
|---|---|
| 会话元信息 | SQLite `sessions`（标题、项目、创建者、状态、`dsh_session_id`、时间） |
| 用户消息 | `turns.user_content + user_name` |
| Agent 回复 | 该 turn 的 `final` 事件 |
| CLI 轨迹 | `events`（thinking / tool_call / tool_result / text / final / error） |
| 模型上下文 | dsh 自己的会话文件：`data/dsh/<agentId>/sessions/...`（由 `dsh_session_id` 指向） |
| 代码与产物 | 沙箱 `workspace` / `artifacts`（设计目标） |
| 终端日志 | 沙箱 `logs/<sessionId>.log`（设计目标） |

聊天消息不是单独存的，由 `turns + final 事件` 派生；前端每次打开会话重新请求。

### 10.2 已知问题

- `events` 无限增长，长会话性能差（P1 分页/裁剪）
- 删除会话不会删除 dsh 会话文件，磁盘会累积
- 会话内容未加密，保留策略未定义

### 10.3 上云建议

- `sessions / turns / events` 迁到 Postgres；大体积事件 payload 可放对象存储，库里存引用
- dsh 会话文件按项目卷/对象存储管理，会话删除或归档时同步清理
- 产物与日志按保留期归档，支持导出与彻底删除
- 会话内容加密存储，按项目隔离

## 11. 本地与云端映射

| | 本地（Docker Desktop） | 云端 |
|---|---|---|
| 沙箱根目录 | `ORG_OS_SANDBOX_DIR`（默认 `server/data/sandboxes`） | 项目持久卷（PVC / EFS / 本地 NVMe） |
| 仓库克隆 | 沙箱卷内，一次 | 同一项目卷，一次 |
| 会话目录 | `worktrees/<sessionId>` | 项目卷子目录 |
| 容器 | 每会话一个容器 | 每会话一个 Pod/容器 |
| 产物 | 卷内 `artifacts/` | 对象存储归档 + 近期保留 |
| 终端 | `docker exec` + PTY | `kubectl exec` / 容器运行时 exec |

云端注意：

- 多节点可跑同一项目时，卷需 `ReadWriteMany`；或做**项目亲和调度**（同一项目固定节点，用本地磁盘）
- 资源限制（CPU/内存/网络）在容器/Pod 层设置
- 项目删除时删除整个卷；删除/归档会话时清理 worktree 与容器

## 12. 工作区清理

- 项目创建/首次使用：创建沙箱卷，克隆仓库
- 会话开始：fetch → 会话分支 → worktree → 容器
- 提交 / 推送 / MR：由改动栏触发，与“会话结束”无关
- 合并/放弃/删除会话：worktree remove → 分支清理 → 产物按保留期处理
- 项目删除：删除卷、容器、相关 dsh 会话文件
- 定期任务：清理孤儿 worktree、过期 artifacts、空闲容器、孤立 dsh 文件

## 13. 待确认与风险

1. **最终容器粒度**：推荐每会话一个容器；每项目一个常驻容器更省但只能项目级串行
2. **node_modules 共享**：pnpm store 共享较安全；软链 node_modules 在 agent 安装依赖时有污染风险
3. **dsh 会话与 cwd**：dsh 会话文件按 cwd 分桶，切换 worktree 后 `--session-id` 能否续接需要验证
4. **多节点存储**：ReadWriteMany 性能 vs 项目亲和调度，需要结合云环境选择
5. **合并权限**：哪些角色可以直接合并，哪些必须走 MR
6. **产物保留期**：测试报告、构建产物保留多久、是否入对象存储

## 14. 验收标准

1. 新建项目必须选择「研发 / 非研发」；非研发项目不显示「代码」「终端」tab，也不创建沙箱卷或容器
2. 新建研发项目**不会启动 Docker**；纯问答会话同样不启动项目容器，不创建 worktree
3. 会话默认 `chat`；**只能**通过「检测到代码操作 → 用户确认」升级为 `code`，没有创建时选择或手动切换
4. 用户拒绝升级后本会话不再重复提示；`code` 不会回退 `chat`，需要纯问答请新建会话
5. 只有 `code` 会话、用户确认后的终端或代码操作才启动容器；空闲后停止、卷保留
6. 研发 git 项目：代码会话 A/B 各自 worktree，互不影响；合并走分支/MR
7. 同一项目默认串行；worktree 模式可并行（可配置）
8. 非 git 项目：serial 模式下不会并发写同一目录
9. 非研发项目：不复制代码，产出进入 `artifacts/<sessionId>/`
10. 终端 tab 可打开项目沙箱，CPU/内存/网络限制生效
11. 删除/归档会话后清理 worktree；项目删除后卷与容器被移除
12. 会话内容刷新后完整；删除会话后 dsh 会话文件被清理（目标）
13. 未提交改动时输入框上方显示 `+x −y · n 个文件`，可提交、可查看 diff、可推送并创建 MR
14. hover 显示文件列表与首个 diff 片段，完整 diff 通过面板查看

## 15. 基础层实现状态（2026-10-25）

已实现：

- 新建项目必选「研发 / 非研发」；`projects.project_type` / `workspace_mode` 落库，类型创建后服务端不可修改
- 非研发项目不显示「代码」「终端」tab，`/api/projects/:id/sandbox` 返回 `disabled`
- 研发项目创建沙箱目录：`ORG_OS_SANDBOX_DIR || <DATA_DIR>/sandboxes/<projectId>/{repos,worktrees,artifacts,logs,home,meta.json}`
- Docker 沙箱：项目专属容器/网络，CPU/内存/pids 限制，只读根、cap-drop、非 root uid；容器按需启动、空闲停止、卷保留
- Sandbox API：`GET /api/projects/:id/sandbox`、`POST .../start`、`POST .../stop`（Cookie 鉴权 + 项目成员校验）
- 终端 tab：xterm + WebSocket + node-pty，`docker exec -it <container> bash`，支持 resize；Docker 未运行时显示明确提示
- 默认镜像 `ubuntu:latest`（可用 `ORG_OS_SANDBOX_IMAGE` 覆盖）；限制可用 `ORG_OS_SANDBOX_CPUS/MEMORY/PIDS` 覆盖

尚未实现（下一阶段）：真实仓库 URL/凭证与 clone/fetch、worktree、diff 栏、commit/push/MR、chat/code 确认式升级。仓库配置与同步方案见 [协作中心-代码仓库配置与同步-技术方案.md](协作中心-代码仓库配置与同步-技术方案.md)。
