# 「项目中心 · 自动化任务」人机交互改造方案

> 创建日期：2026-08-28
> 更新日期：2026-08-28

## 1. 背景与目标

### 1.1 现状问题

当前 `AutomationPanel` 只回答"配置了哪些任务"，存在三个缺口：

| # | 问题 | 现状表现 |
|---|---|---|
| 1 | **运行状态不可见** | 只有一个静态徽标（成功/失败/运行中），看不到执行到哪一步、跑了多久、日志输出什么 |
| 2 | **人无法介入** | 任务运行是黑盒：不能在中途暂停等人确认，也不能在运行中向任务补充信息 |
| 3 | **没有通知** | 任务卡住/需要人处理时，人毫无感知，必须自己进到这个 tab 才能发现 |

### 1.2 改造目标

1. **运行状态可视化**：步骤级时间线 + 实时推进（运行中 → 步骤完成 → 成功/失败），徽标与进度联动；
2. **人工介入（Human-in-the-loop）**：任务可在运行中"停下来等人"——
   - **确认点**：暂停等人「批准 / 拒绝」（如：发布前确认内容）；
   - **输入点**：暂停等人**填写表单**后继续（如：填写发布版本号）；
3. **通知**：应用内通知中心（标题栏铃铛 + 角标 + 下拉列表），待处理事项一目了然，可从通知直接处理或跳转；
4. 布局不拘泥 table：采用 **行式列表 + 行内展开运行详情**（保留表格的可扫读性，但展开详情、表单、时间线在纯 table 里体验差）。

## 2. 核心概念与状态机

### 2.1 概念模型

```
任务 Job（配置：触发方式/参数/启停）
 └── 运行 Run（一次执行实例，有自己的状态）
      ├── 步骤 Step（拉取代码 → 构建 → 单元测试 → 发布…）
      └── 人工介入点 Gate（运行到某步时暂停等人）
           ├── 确认型：等人 [批准] / [拒绝]
           └── 输入型：等人填表单后 [提交并继续]
```

- 一个任务同一时刻最多一个「当前运行」；历史运行保留最近 3 条（Mock）。
- 通知（Notification）由 Gate 触发产生，Gate 被处理后消失。

### 2.2 运行状态机

```
                 ┌──────────[批准]──────────┐
                 ▼                          │
 排队中 ──▶ 运行中 ──▶ 等待确认 ──[拒绝]──▶ 已拒绝（终态）
              │  ▲
              │  └──────[提交表单]──────────┤
              ├──▶ 等待输入 ──[取消]──▶ 已取消（终态）
              │
              ├──▶ 成功（终态）
              └──▶ 失败（终态）
 （运行中/等待中 均可被人工「取消运行」→ 已取消）
```

### 2.3 状态徽标配色（沿用现有语义色变量）

| 状态 | tone | 说明 |
|---|---|---|
| 排队中 | neutral 灰 | |
| 运行中 | info 蓝 + **脉冲动画点** | 唯一带动态效果的徽标，一眼识别"正在跑" |
| 等待确认 | warning 橙 | 需要人行动 |
| 等待输入 | warning 橙 | 需要人行动（徽标文字区分） |
| 成功 | success 绿 | |
| 失败 | danger 红 | |
| 已取消 / 已拒绝 | neutral 灰 | 人为终止，非故障 |

## 3. 页面布局（推荐方案 A）

面板整体仍遵守 Settings 极简风（分组卡片 + 行式布局），自上而下三段：

```
┌────────────────────────────────────────────────────────────────┐
│ 共 4 个任务 · 4 个启用 · 1 个运行中 · 2 个待人工处理（橙色高亮）  │
│                                                                │
│ ⚠ 待人工处理（2）                                               │
│ ┌────────────────────────────────────────────────────────────┐ │
│ │ ▎周报生成 · 运行 #r12                          [等待确认]   │ │ ← 左侧3px橙色边条
│ │ ▎即将把周报发布到外部渠道，请确认内容无误。                   │ │
│ │ ▎运行至步骤 3/4 · 已等待 5 分钟                 [拒绝][批准] │ │
│ ├────────────────────────────────────────────────────────────┤ │

│ └────────────────────────────────────────────────────────────┘ │
│                                                                │

│ │    定时 · 每天 08:00 · 执行中：单元测试                      │ │
│ │    ▸ 展开运行详情                                (●─) 开    │ │
│ │  ┌─（展开区）─────────────────────────────────────────────┐ │ │
│ │  │ 运行 #r11 · 开始于 08-28 08:00            [取消运行]    │ │ │
│ │  │  ✓ 拉取代码                                   08:00:02  │ │ │
│ │  │  ✓ 安装依赖                                   08:00:41  │ │ │
│ │  │  ● 单元测试（当前步骤，蓝点脉冲）                       │ │ │
│ │  │  ○ 构建产物                                            │ │ │
│ │  │  ────────────────────────────────────────────────────  │ │ │
│ │  │  08:00:01  拉取 origin/dev … done                     │ │ │
│ │  │  08:00:41  依赖安装完成，共 312 个包                    │ │ │
│ │  └────────────────────────────────────────────────────────┘ │ │
│ ├────────────────────────────────────────────────────────────┤ │
│ │ MR 静态检查                                     [成功]      │ │
│ │    事件 · MR 创建时 · 上次 08-26 13:40 · 耗时 2 分 10 秒     │ │
│ │    ▸ 展开运行详情                     [运行]      (●─) 开   │ │
│ └────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────┘
```

**三段说明**：

1. **顶部汇总行**（灰字）：任务数 / 启用数 / 运行中数 / **待人工处理数**（>0 时橙色，点击滚动定位到待处理分组）；
2. **「待人工处理」分组**（仅当有等待中的运行时出现，置顶）：
   - 每条 = 一个等待中的运行卡片，左侧 3px 橙色边条（全面板唯一彩色强调，语义 = 需要人行动）；
   - **确认型**：说明文案 + 行内 `[拒绝] [批准]`，无需展开即可处理；
   - **输入型**：说明文案 + 表单字段（必填校验，空则提交禁用）+ `[提交并继续]`；
   - 处理完成后卡片消失，任务回到下方列表正常位置；
3. **「任务」列表**（行式，同现有风格）：
   - 行左侧：任务名 + 触发方式 · 当前执行步骤/上次结果 · 耗时；
   - 行右侧：运行状态徽标（运行中带脉冲点 + 步骤进度 `2/4`）+ 空闲任务显示 `[运行]` 文字按钮（手动触发一次，方便演示）+ 启停开关；
   - 点击行展开**运行详情**：步骤时间线（✓ 已完成绿 / ● 当前蓝脉冲 / ○ 待执行灰空心）+ 尾部日志（等宽小字，最近 6 行）+ `[取消运行]`（运行中/等待中显示）；
   - 等待中的任务行徽标为橙色，但操作统一收在上方待处理分组，行内不重复放按钮（避免两处状态不同步）。

**为什么不用纯 table / 左右分栏**：

- 纯 table：行内展开的时间线、日志、输入表单塞进表格单元格体验差；列宽被锁死，"执行中：单元测试"这类动态文案换行难看；
- 左右分栏（列表 | 详情）：详情页面板宽仅 720px，再分栏两侧都太窄；
- 行式列表 + 展开保留了 table 的"一行一任务、列对齐可扫读"，又给详情留出整行宽度。

> 备选方案 B（不推荐但列出）：不做独立待处理分组，等待中的任务在列表内置顶 + 橙色高亮，点行展开后顶部显示人工介入卡片。结构更简单（无重复展示），但确认操作要多一次点击、视觉优先级不够。

## 4. 通知设计

### 4.1 入口：标题栏铃铛

- 标题栏右侧（侧边栏切换图标旁）新增铃铛图标；有待处理通知时显示红色角标（数字）；
- 铃铛在**任何页面**都可见——人可能正在对话页工作，任务卡住了也要能感知（这是"需要通知"的核心）。

### 4.2 通知下拉

```
┌ 通知（2 条待处理）──────────────────────┐
│ [等待确认]  周报生成 · 运行 #r12          │
│ 即将把周报发布到外部渠道，请确认内容无误    │
│ 5 分钟前                  [拒绝] [批准]   │
├────────────────────────────────────────┤
│ [等待输入]  发布准备 · 运行 #r9           │
│ 发布前请补充版本号与发布说明               │
│ 12 分钟前                     [去填写 →]  │
└────────────────────────────────────────┘
（无待处理时：空状态「暂无待处理通知」）
```

- 宽约 320px，白底圆角卡片下拉，样式沿用 Dropdown 的浮层语言；
- **确认型**：通知项内直接给 `[拒绝] [批准]` 快捷按钮（最短路径）；
- **输入型**：`[去填写 →]` 跳转——切换到对应项目详情 → 自动化任务 tab → 展开该任务行并滚动定位到待处理卡片；
- Gate 被处理（任一入口）后，对应通知即时消失、角标 -1。

### 4.3 跳转链路（Mock 内实现）

```
通知点击 → App.setView(project-detail + initialNav='automation')
        → ProjectDetail 支持外部指定初始导航项
        → AutomationPanel 接收 focusJobId，展开对应行 + scrollIntoView
```

## 5. 交互流程与 Mock 模拟

纯前端 Mock，用 `setTimeout` 链模拟运行推进（不引入定时轮询框架）。

### 5.1 初始场景（loomweb 项目）

| 任务 | 初始状态 | 用途 |
|---|---|---|
| 每日构建 | **运行中**（步骤 2/4：单元测试） | 演示实时推进 |
| 周报生成 | **等待确认**（已等 5 分钟，通知已有 1 条） | 演示确认流 |
| 发布准备（新增） | **等待输入**（已等 12 分钟，通知已有 1 条） | 演示输入流 |
| MR 静态检查 | 空闲 · 上次成功 | 演示「运行」手动触发 |

### 5.2 推进脚本

- **每日构建**：t+4s 步骤2完成 → t+8s 步骤3 → t+12s 全部完成 → 徽标变「成功」，行内显示总耗时；期间时间线节点逐个变绿、日志逐行追加；
- **批准**（周报生成）：卡片消失 → 通知消失 → 任务行变「运行中」→ t+5s「成功」；
- **拒绝**：卡片消失 → 通知消失 → 任务行变「已拒绝」（灰），历史记录保留；
- **提交表单**（发布准备）：校验必填 → 卡片消失 → 「运行中」→ t+5s「成功」；
- **取消运行**：任意活动状态可点 → 「已取消」（灰）；
- **[运行] 手动触发**（MR 静态检查）：从头跑一遍 4 步推进脚本；若新建任务时勾选了「运行中需要人工确认」，则跑到一半进入等待确认并触发通知。

### 5.3 编辑约束（沿用并扩展现有规则）

- 运行中 / 等待中 / 排队中的任务：**不可编辑、不可删除、启停开关禁用**（提示「运行中的任务不可修改」），终止手段是「取消运行」；
- 新建任务弹窗新增一个开关字段：「运行中需要人工确认」（默认关）——开启后该任务每次运行到中点会暂停等待批准，让新建任务也能演示人机交互。

## 6. 数据模型（`data/projects.ts` 改造）

```ts
/** 运行步骤状态 */
export type StepStatus = '等待' | '运行中' | '成功' | '失败' | '跳过'

export interface RunStep {
  id: string
  name: string
  status: StepStatus
  /** 完成时刻（如 08:00:41） */
  time?: string
}

/** 人工介入点 */
export interface HumanGate {
  type: '确认' | '输入'
  title: string
  description: string
  /** 输入型：表单字段定义 */
  fields?: { key: string; label: string; placeholder?: string; required?: boolean }[]
}

export type RunStatus =
  | '排队中' | '运行中' | '等待确认' | '等待输入'
  | '成功' | '失败' | '已取消' | '已拒绝'

/** 任务的一次运行 */
export interface JobRun {
  id: string
  jobId: string
  status: RunStatus
  startedAt: string
  finishedAt?: string
  steps: RunStep[]
  /** 当前执行到的步骤下标 */
  currentStep: number
  /** 等待中的人工介入点（非等待状态为空） */
  gate?: HumanGate
  /** 已等待时长（等待状态显示用） */
  waitingSince?: string
  /** 运行日志尾部（最近若干行） */
  logs: string[]
}

export interface AutoJob {
  id: string
  name: string
  triggerType: '定时' | '事件' | '手动'
  triggerParam: string
  enabled: boolean
  /** 运行中需要人工确认（新建任务可勾选） */
  needApproval: boolean
  /** 当前运行（无则空闲） */
  currentRun?: JobRun
  /** 历史运行（Mock 保留最近 3 条） */
  history: JobRun[]
}

/** 应用内通知 */
export interface Notification {
  id: string
  /** 关联的 gate 类型 */
  type: '等待确认' | '等待输入'
  jobId: string
  runId: string
  projectId: string
  title: string
  description: string
  /** 相对时间文案 */
  time: string
}
```

> 原 `lastStatus: string` / `lastRun: string` 字段删除，由 `history`（取最新一条）替代；`AutomationPanel` 重写，无兼容负担。

## 9. 验收标准

1. 顶部汇总四项数字随状态实时联动，「待人工处理」>0 时橙色可点击定位；
2. 运行中任务：徽标脉冲 + 步骤进度（2/4）+ 展开可见时间线逐节点推进、日志逐行追加，最终变「成功」并显示总耗时；
3. 等待确认：铃铛角标出现 → 下拉内可直接批准/拒绝；面板待处理卡片同样可操作；两个入口处理任一后，另一处即时同步消失；
4. 等待输入：表单必填校验（空则提交禁用），提交后卡片消失、任务继续运行至成功；
5. 「取消运行」在运行中/等待中可用，结果为灰色「已取消」；
6. 空闲任务「运行」按钮可手动触发一次完整运行；勾选了确认开关的任务运行至中点会暂停并触发通知；
7. 通知「去填写」能跳转到对应项目 → 自动化任务 tab → 展开并定位到该任务；
8. 运行中/等待中任务不可编辑/删除，启停开关禁用并有提示；
9. 视觉遵守 Settings 极简风（唯一彩色强调 = 待处理卡片橙色左边条）；构建通过，提交 commit。

## 10. 风险与说明

- 纯 Mock：运行推进用 setTimeout 模拟，刷新页面重置；不对接真实调度后端，后续引擎接口化即可替换；
- 通知仅应用内（铃铛），真实系统的 IM/邮件推送不在本期范围；
- 历史运行仅保留最近 3 条，不做运行历史列表页（后续可扩展）；
- 组件卸载/切换项目时需清理定时器，避免内存泄漏与跨项目状态污染（engine 内统一管理）。
