# 项目中心 · 详情页四格列宽比例调整（10% / 20% / 35% / 35%）—— 技术方案

> 创建日期：2026-10-22
> 更新日期：2026-10-22（实施完成：含实测数据与两处实施期修正——格 2 min 200→180、grid 加 overflow-x 兜底）

## 1. 需求

鹿鹿子大王要求：详情页四格默认分配比例改为 **10% / 20% / 35% / 35%**。

即：格 1 会话列表 10%、格 2 会话详情 20%、格 3 Agent CLI 35%、格 4 工作流 35%。
（格 3 与格 4 各占最大份额，利于展示 agent CLI 完整轨迹与工作流画布。）

## 2. 现状与差距

### 2.1 现状机制：px 定宽 + 末格 flex 吸收

```tsx
// ProjectDetail.tsx
const COLUMN_SPECS = [
  { defaultWidth: 168, minWidth: 120 }, // 格 1 会话列表
  { defaultWidth: 298, minWidth: 200 }, // 格 2 会话详情
  { defaultWidth: 233, minWidth: 160 }, // 格 3 Agent CLI
]
```

- 格 1/2/3：JS 内联 `flex: 0 0 {w}px` 定宽
- 格 4：`.detail-cell.detail-config { flex: 1 1 auto; min-width: 240px }` 吸收剩余

### 2.2 为什么不能只改数字

| 问题 | 说明 |
|---|---|
| **px 无法表达比例** | 窗口现已「贴边占满桌面」（宽度随显示器变化）。写死 px 时，宽屏下四格仍是 168/298/233，比例失真（格 1 占比从 10% 掉到 6%） |
| **百分比 width 会溢出** | 四格的百分比基准是 `.detail-grid` 内容宽，**不含** 3 根 6px 拖拽条（18px）与 8px padding（16px）。直接 `width: 35%` 四格相加 = 100% + 34px → 溢出 |
| **末格 flex 吸收与比例冲突** | 即使格 1-3 用百分比，格 4 是「吸收剩余」，其实际宽 = 余量 ≠ 35%（窄窗口下偏差约 18px） |

→ 结论：**必须把机制从「px 定宽 + 末格吸收」改为「flex 比例分配」**，而不是调数值。

## 3. 方案

### 3.1 核心：改用 flex-grow 比例分配（精确、自适应）

四格统一按 `flex: <ratio> 1 0px` 渲染，ratio = 10 / 20 / 35 / 35：

```tsx
const COLUMN_SPECS = [
  { ratio: 10, minWidth: 96 },  // 格 1 会话列表
  { ratio: 20, minWidth: 200 }, // 格 2 会话详情
  { ratio: 35, minWidth: 160 }, // 格 3 Agent CLI
  { ratio: 35, minWidth: 240 }, // 格 4 工作流
]
```

```tsx
<div className="detail-cell" style={{ flex: `${ratio} 1 0px` }}>
```

**为什么用 flex-grow 而非 `width: 10%`**：

- flex 容器分配的是**扣除 padding 与固定项（3×6px 拖拽条）后的剩余空间**，按 grow 比例分 → 四格比例精确 10:20:35:35，**不会溢出**
- 任意窗口宽/缩放都自动保持比例（无需 JS 监听 resize 重算）
- 四格地位对称（不再有「末格特殊」），语义更干净

代价：比例基准是「主区宽 − 拖拽条 18px」，非主区总宽。以主区 1350px 为例，10% ≈ 130px（vs 严格的 135px），偏差 ≤ 1.5%，用户不可感知。

### 3.2 拖拽后的分配语义

| 状态 | 渲染 | 说明 |
|---|---|---|
| 默认（未拖过） | 四格 `flex: <ratio> 1 0px` | 比例分配 |
| 拖拽后 | **被拖格** `flex: 0 0 <px>px`（固定），**其余三格**仍 `flex: <ratio> 1 0px` | 拖动某格 = 固定该格宽，剩余空间由其他三格按比例重分配 |

- 拖拽体验：拖宽格 1 → 格 2/3/4 按 20:35:35 等比压缩；再拖回来 → 恢复比例
- 双击拖拽条 `reset()` → 清空所有 px 覆盖，四格回默认比例（与现有行为一致）

### 3.3 顺带修正：拖拽起点改读真实 DOM 宽度

**现状问题**：`useResizableColumns` 首次 `mousemove` 时用 `specs[i].defaultWidth` 作为起始宽。
改成比例渲染后，实际宽度与 spec 数值无对应关系 → 拖拽会**跳变**。

**修正**：`mousedown` 时直接读左侧格真实渲染宽（`e.currentTarget.previousElementSibling.getBoundingClientRect().width`），
作为 `startWidth` 记录。这也顺带修掉了原实现在「容器宽 ≠ 设计宽」时的起点偏差。

### 3.4 溢出防护：max 钳制

被拖格变宽时，其余格按比例缩小、触到 `min-width` 后不再缩 → 继续拖会溢出容器。

**方案**：`max = 容器内容宽 − 拖拽条(18px) − 其余三格 minWidth 之和`，拖拽时 `clamp(minWidth, startWidth + delta, max)`。

### 3.5 min 宽度适配（需确认）

默认比例在常用窗口下的落地检查（主区约 1350px，可用宽 = 1350 − 16 − 18 = 1316px）：

| 格 | 目标比例 | 实算宽 | 现 min | 是否触底 |
|---|---|---|---|---|
| 1 会话列表 | 10% | ≈132px | 120 | 不触底 ✓ |
| 2 会话详情 | 20% | ≈263px | 200 | 不触底 ✓ |
| 3 Agent CLI | 35% | ≈461px | 160 | 不触底 ✓ |
| 4 工作流 | 35% | ≈461px | 240 | 不触底 ✓ |

窄窗口（1280 桌面，主区约 1022px，可用宽 988px）：

| 格 | 目标 | 实算宽 | 影响 |
|---|---|---|---|
| 1 | 10% | ≈99px | 现 min 120 → **触底，比例失真为 12.1%** |

→ **实施结果**：格 1 `minWidth` 120 → **96px**（保证 1022px 主区下 10% 生效）；
格 2 实施中由 200 → **180px**（1280 视口下 20% ≈ 195px，原 200 会触底致比例失真，见 6.6）。
代价：格 1 最窄时头像 + 两行文字略挤（会话名已 ellipsis，可接受）。

最终 COLUMN_SPECS（`ProjectDetail.tsx`）：

```tsx
const COLUMN_SPECS = [
  { ratio: 10, minWidth: 96 },  // 格 1 会话列表
  { ratio: 20, minWidth: 180 }, // 格 2 会话详情
  { ratio: 35, minWidth: 160 }, // 格 3 Agent CLI
  { ratio: 35, minWidth: 240 }, // 格 4 工作流
]
```

## 5. 影响面与风险

- **范围**：仅四格默认宽度分配 + 拖拽起点计算；不动各格内部组件、不动会话/数据逻辑
- **风险**：低。比例分配为纯 CSS flex 行为，无副作用；双击重置、拖拽条样式、min 钳制均保留
- **回退**：若比例不合适，只需改 `COLUMN_SPECS` 的 ratio 数字（单点）

## 6. 验证结果（已通过）

### 6.1 比例精度（Playwright 亚像素测量）

**关键点**：`flex-basis: 0px` 的分配基准是**内容盒**（不含 border/padding），
故可分配基线 = `clientWidth − padding − resizer 和 − 四格边框和`：

| 视口 | grid clientWidth | 可分配基线 | 实算（内容盒） | 比例误差 |
|---|---|---|---|---|
| 1600×900 | 1330 | 1288 | 128.8 / 257.6 / 450.8 / 450.8 | **0.000 pp** |
| 1280×800 | 1010 | 968 | 96.8 / 193.6 / 338.8 / 338.8 | **0.000 pp** |

**溢出校验**（两视口均成立）：

- 1600：四格和 1296.01 + resizer 18 + padding 16 = 1330.01 ≈ clientWidth 1330（差 0.01px 亚像素舍入），`scrollWidth − clientWidth = 0`
- 1280：976.01 + 18 + 16 = 1010.01 ≈ 1010，无横向溢出

**自适应**：1600 → 1280 → 1600 全程用 MutationObserver 监听 `.detail-grid` 子树 style 变化 → **styleMutations = 0**，
四格 inline style 始终为原始 `flex: 10/20/35/35 1 0px`，宽度变化 100% 由 flex 布局自动完成（无 JS 重算）。

### 6.2 拖拽行为（真实 mouse 事件）

拖第 1 根 resizer 向右 +120px：

| | 格 1 | 格 2 | 格 3 | 格 4 |
|---|---|---|---|---|
| 拖前 | 130.80 | 259.61 | 452.80 | 452.80 |
| 拖后 | **250.80**（+120.00 ✓） | 232.94 | 406.13 | 406.14 |
| Δ | +120.00 | −26.67 | −46.67 | −46.66 |

其余三格按 **20 : 35 : 35** 精确等比缩小；总量守恒（四格和拖前=拖后=1296.01），**无溢出**。

**极限钳制**：

- 向右猛拖 +2000px → 格 1 被 max 钳为 **716px**（= `1314 − 18 − (180+160+240)`），其余三格恰为各自 min 180/160/240，不破 min、不溢出
- 向左猛拖 −2000px → 格 1 钳到自身 min **96px**，其余扩为 267.33/466.34/466.33，总量守恒

### 6.3 双击重置

双击 resizer → 四格恢复 130.80 / 259.61 / 452.80 / 452.80，与默认值**逐像素一致（Δ = 0.00 ×4）**。

### 6.4 极窄视口兜底（实施期新增）

900×800 视口：`.detail-grid` clientWidth 630 / scrollWidth 710 → 横向滚动被 grid 吸收 80px，
`documentElement.scrollWidth = 900 = 视口宽`，**窗口未被顶破**（若不加 `overflow-x: auto`，min 之和 696 + 18 + 16 = 730 > 630 会直接顶破 body）。

### 6.5 亲自读图

1600 与 1280 两张整页截图：格 1 窄（头像 + 会话名省略）、格 2 中等、格 3 Agent CLI 与格 4 工作流各占 35%，
比例符合预期，Agent CLI 轨迹展示空间充足，无裁切、无横向滚动条。

## 6.6 实施期两处修正（超出原方案）

| 修正 | 原方案 | 实施后 | 原因 |
|---|---|---|---|
| 格 2 minWidth | 200 | **180** | 实测发现 1280 视口（极常见笔记本分辨率）下 20% ≈ 195px 会触到 min 200，导致格 3/4 各被压到 34.09%；降到 180 后 1280 下不触底，比例精确 |
| `.detail-grid` | 无 overflow 声明 | **`overflow-x: auto`** | 四格 min 之和 + 拖拽条 + padding = 730px 是硬下限，更窄视口（如 900）会顶破窗口；加横向滚动兜底 |
