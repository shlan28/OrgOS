# 协作中心 · 会话团队协作改造方案（P0 / P1）

> 日期：2026-10-25
> 目标：把当前「单人 + 单个 agent」的会话，改造成项目成员可共同参与、消息串行执行、身份可追溯的团队会话。
> 范围：P0 为协作可用性与安全底线，P1 为协作体验与工程质量。

## 0. 已确认的产品决策

1. **会话成员 = 项目成员**：不新增 `session_participants`，不做“会话私有 / 邀请某人”的独立成员模型；能进项目就能进该项目的会话。
2. **Agent 归属项目，不归属会话**：项目里绑定的 agent 全部默认可用；新建会话不再选择或绑定 agent；会话列表/详情不按 agent 区分归属。
   - 自动执行使用**项目主 agent**（项目绑定的第一个 agent）；其余 agent 在会话中展示、可被 @ 提及，暂不自动分工
   - 后续可通过 `@agent` 指定本条消息的执行者（不在本次范围）
3. **多人消息排队执行**：同一会话同一时间只执行一个 turn，新消息进入队列，按先后顺序执行。

以下设计均以这三条为前提。

## 1. 现状问题（本次要解决的）

### P0 级

| # | 问题 | 影响 |
|---|---|---|
| P0-1 | `/api/*` 没有任何鉴权；登录只在前端 | 任何人都能读写全部项目/会话/Agent，SSE 也能匿名订阅 |
| P0-2 | `turns` 不存发送者，前端把 user 消息都渲染成当前登录用户 | 多人同会话无法区分谁说了什么 |
| P0-3 | `sessions` 没有 `created_by` | 看不出谁发起的会话 |
| P0-4 | 发送即执行，无队列；并发时两个 dsh 进程续接同一会话文件 | 上下文互相覆盖、会话文件损坏风险 |
| P0-5 | `MAX(seq)+1` 非事务且无唯一约束 | 并发写入产生重复 seq |
| P0-6 | 会话只有单一 `status` 字段 | 多个 turn 时状态互相覆盖，agent 状态误判 |
| P0-7 | 创建会话不校验 agent 是否属于该项目；改名/删除/发送不校验项目成员 | 越权与数据错绑 |
| P0-8 | 删除会话不取消运行中的 turn | 进程继续写已删除的 turn/event，外键异常可能打挂服务 |
| P0-9 | 软删除项目后，其会话仍可读写 | 已删除项目的数据仍可被操作 |
| P0-10 | 服务重启后 `running` 状态不复位 | 会话与 agent 永久显示“运行中/工作中” |
| P0-11 | 同一 agent 的所有会话共享 `workdir` | 不同用户/会话互相覆盖代码（P1 处理隔离，P0 先保证同会话串行） |

### P1 级

| # | 问题 | 影响 |
|---|---|---|
| P1-1 | 只有自己 turn 的 SSE，别人的消息/状态不推送 | 多人协作必须手动刷新 |
| P1-2 | 无未读、无最后活动排序、无创建者展示 | 会话列表无法支撑团队协作 |
| P1-3 | 消息不显示时间；失败 turn 在历史里没有错误气泡 | 回溯困难 |
| P1-4 | 会话列表宽 10%，每行常驻“空闲” | 标题截断、信息噪音 |
| P1-5 | 加载/创建/改名/发送失败只 `console.error` | 用户无反馈 |
| P1-6 | “会话成员”抽屉实际是项目成员 + 全部 agent | 命名误导（按决策改为项目成员/项目 agent） |
| P1-7 | `messages` 接口 N+1 查询、`events` 全量返回 | 长会话性能差 |
| P1-8 | 新会话标题前端按列表长度生成；改名长度前后端不一致（40/100） | 重名、校验不一致 |
| P1-9 | 真实会话头像颜色全部落默认灰蓝 | 视觉无法区分 |
| P1-10 | 删除 Agent 会级联删除其全部会话，无提示 | 误删不可恢复 |
| P1-11 | 成员在线状态是种子数据，从不更新 | 在线点不可信 |
| P1-12 | 同 agent 不同会话并行共享工作区 | 文件互相覆盖（需会话级工作区隔离） |

## 2. 目标模型

### 2.1 身份与权限

**根因**：当前 `getCurrentUser()` 读写的是 `org_settings` 里的全局当前用户，本质上只支持一个登录身份，多人同时登录会互相覆盖。必须先改成真正的 per-request 身份。

新增 `auth_sessions`：

| 字段 | 说明 |
|---|---|
| `token` | 随机 token（主键），放入 HttpOnly Cookie `org_session` |
| `user_name` | 登录用户名 |
| `permission` | 登录时快照的权限（所有者/管理员/成员） |
| `created_at` / `expires_at` / `last_seen_at` | 生命周期（默认 7 天） |

- 登录（密码 / 飞书 OAuth）成功后创建 token 并 `Set-Cookie`（HttpOnly、SameSite=Lax、Path=/）
- 退出登录删除 token 并清 Cookie
- 中间件 `requireAuth`：解析 Cookie → 挂 `req.user`；`/api/auth/*`、`/api/health` 放行
- 所有业务路由改用 `req.user`，不再使用全局 `getCurrentUser()`
- EventSource 同源请求会自动携带 Cookie，SSE 同样受保护

**项目访问规则**：
- 所有者 / 管理员：可访问全部项目
- 成员：只能访问自己作为成员的项目（`project_members.name = req.user.name`）
- 文件夹的 `members` 暂不参与访问控制（保持现状，后续再收紧）
- 所有会话接口先解析 session → project → 校验成员身份；项目软删除（`deleted_at` 非空）返回 404

### 2.2 会话与消息

**sessions 新增/调整**

| 字段 | 说明 |
|---|---|
| `created_by` | 创建者用户名 |
| `last_message_at` | 最后一条消息时间（列表排序用） |
| `status` | `idle` / `queued` / `running`（由队列派生并维护） |
| `agent_id` | 保留列（NOT NULL 约束）；新会话写入项目主 agent 仅作兼容，**不作为会话归属**；每个 turn 执行时重新解析并记录实际 agent |

**turns 调整**

| 字段 | 说明 |
|---|---|
| `user_name` | 发送者用户名（必填） |
| `agent_id` / `agent_name` | 实际执行该 turn 的 agent（执行时写入） |
| `status` | `queued` / `running` / `done` / `error` / `canceled` |
| `error` | 失败原因 |

- 唯一约束 `UNIQUE(session_id, seq)`，seq 生成放在事务内
- 消息列表返回：用户消息带 `user_name`；agent 消息带 `agent_name`
- 历史数据：`user_name` 为空的 turn 显示“未知成员”，`created_by` 为空显示“未知”

### 2.3 执行模型（排队）

**规则**
- 同一会话：FIFO 串行，同一时刻最多一个 dsh 进程
- 不同会话：并行（P0 不限制；P1 通过工作区隔离解决同 agent 冲突）
- **执行 agent 解析**：turn 开始时取「项目当前绑定的第一个 agent（按创建时间）」；项目内其他 agent 展示在会话中但暂不自动分工；实际执行者写入 turn
- 项目没有 agent：新建会话按钮禁用，发送接口返回 400

**流程**

```
发送消息
  → 事务写入 turn(status=queued, seq)
  → session.status = running/queued，last_message_at 更新
  → 若该会话没有 worker，启动 worker

worker（内存 Map<sessionId, 运行中 Promise>）
  → 取下一条 queued turn（按 seq）
  → 标记 running，解析项目主 agent
  → spawn dsh（沿用 runner.js）
  → 流式事件落库 + 推送
  → 结束：标记 done/error，更新 session 状态
  → 若还有 queued，继续下一条；否则退出 worker
```

**状态派生**
- 任一条 `running` → 会话 `running`
- 无 running 但有 `queued` → 会话 `queued`
- 都没有 → `idle`
- Agent 的“工作中”仍由 `sessions.status = running` 派生，保持不变

**取消**
- `queued`：直接从队列移除，标记 `canceled`
- `running`：kill 进程，标记 `canceled`，worker 继续下一条
- 删除会话：先取消队列与运行中 turn，再删除

**重启恢复**
- 启动时把所有 `running` turn 标记为 `error: 服务重启中断`，`running` session 重新派生状态
- 对仍有 `queued` turn 的会话自动启动 worker
- 不需要保留被中断 turn 的进程

## 3. P0 改造清单

### 3.1 后端

1. **鉴权**
   - 新增 `auth_sessions` 表 + `requireAuth` 中间件
   - 登录/登出改为签发/删除 Cookie
   - 业务路由统一使用 `req.user`
2. **项目成员校验**
   - 新增 `assertProjectAccess(req.user, projectId)`：项目存在、未软删、用户是成员或管理员/所有者
   - 项目列表按身份过滤
   - 会话相关路由（列表/创建/改名/删除/消息/事件/发送/取消/SSE）全部走该校验
3. **发送者与创建者**
   - `turns.user_name`、`sessions.created_by`
   - messages 接口返回发送者与 agent 名
4. **排队执行**
   - turn 状态机 + 会话串行 worker（新增 `server/sessionQueue.js`）
   - `createTurn` 改事务、加唯一约束
   - 会话状态派生
   - 执行 agent 解析（项目主 agent），turn 记录实际 agent
5. **运行生命周期修复**
   - 删除会话先取消
   - 软删项目阻断会话接口
   - 启动对账（见上）
6. **接口收敛**
   - `POST /api/projects/:id/sessions` 不再接受 `agentId`
   - `POST /api/sessions/:id/turns` 使用 `req.user` 记录发送者
   - `GET /api/sessions/:id/messages` 返回 `userName` / `agentName` / 错误信息
   - 新增 `GET /api/sessions/:id/queue`（可选，P1 SSE 会更完整）

### 3.2 前端

1. 登录态：沿用 `authApi`，确认 Cookie 模式；退出登录调用后端清 token
2. `ProjectDetail`：会话加载/创建/改名/发送失败要展示错误（不再只 `console.error`）
3. `ChatPane`：user 消息按 `message.senderName` 渲染；agent 消息按 `agentName`
4. 新建会话：去掉 agent 选择；项目无 agent 时禁用并提示
5. `MembersDrawer`：按决策固定展示“项目成员 / 项目 agent（全部可用）”，不叫“会话成员”
6. 队列可见性（P0 最小版）：自己发送后显示“排队中/执行中”状态；等待中的消息在列表中置灰
7. 删除会话入口（可选放编辑项目或 ⋯ 菜单）：确认后调用后端

## 4. P1 改造清单

### 4.1 实时协作

- 新增会话级 SSE：`GET /api/sessions/:id/stream`
  - 事件：`message`（新消息/agent 回复）、`turn`（状态与队列位置）、`session`（标题/状态）、`agent`（工作中/空闲）
  - 前端订阅后即时刷新会话，不再依赖手动刷新
- 会话列表实时化：项目级 SSE 或 5s 轮询（二选一，建议 SSE）
- 未读：
  - 新增 `session_reads(session_id, user_name, last_read_turn_seq)`
  - 列表返回 `unreadCount`；打开会话即标记已读
- Agent 状态刷新不再依赖进入项目/发送动作

### 4.2 会话列表（SessionRail）

- 列宽比例调整（建议 14 / 18 / 33 / 35），保证标题和创建者可读
- 行信息：会话名、创建者、最后活动时间、未读数、状态（运行中/排队中，空闲不显示徽标）
- 排序：`last_message_at` 倒序，运行中优先
- 支持“我的 / 全部”过滤、搜索
- 会话头像颜色：按 session id 哈希生成稳定颜色

### 4.3 聊天区（ChatPane）

- 渲染消息时间（HH:mm:ss）
- 失败 turn 显示错误气泡（后端把 `turns.error` 带进 messages）
- 排队位置提示：“排队中（前面 N 条）”
- 顶部显示创建者、参与者（项目成员）与当前执行 agent
- 空态/加载态/错误态完善

### 4.4 接口与性能

- `messages` 支持分页（`before` / `limit`），前端滚动加载
- 修复 N+1：一次查询 turns + finals（JOIN 或批量查询）
- `events` 按 turn 分页或按需加载；历史 CLI 默认只加载最近 N 轮
- 新会话标题由服务端生成（按项目内最大编号 +1，事务内保证不重名）
- 改名长度统一（建议 60 字），失败返回明确错误码

### 4.5 项目沙箱与工作区隔离

完整设计见 [协作中心-项目沙箱与工作区方案.md](协作中心-项目沙箱与工作区方案.md)，要点：

- 新建项目必选「研发 / 非研发」；**非研发项目不显示「代码」「终端」tab**，不创建沙箱卷或容器
- 区分研发 / 非研发项目，工作区策略：`none`（非研发）/ `serial`（非 git 研发）/ `worktree`（git 研发）
- **一个项目一个持久沙箱卷**：仓库只克隆一次，会话用 worktree 共享 `.git`，不重复拉代码
- 推荐每会话一个容器（Docker）挂载项目卷，按会话限制 CPU / 内存 / 网络
- **Docker 按需启动**：新建项目不启动；纯问答会话也不启动项目容器，只有确认升级为代码模式、并进入执行后才启动，空闲后停止、卷保留
- 会话默认 `chat`，只能通过「检测到代码操作 → 用户确认」升级为 `code`；不支持随意来回切换
- 格 4 新增「终端」tab（仅研发项目），接入项目沙箱容器（xterm + WebSocket + PTY）
- 提交 / push / MR 由输入框上方的未提交改动栏触发，不引入会话生命周期；`idle` 只表示没有运行中的 turn
- 删除会话前提示处理未提交改动与未推送提交
- 非研发项目不复制代码，只读上下文 + `artifacts/<sessionId>/` 输出
- 非 git 项目默认 `serial`；需要并行时可选快照副本；不自动 `git init`

### 4.6 其他

- 删除 Agent 前提示将删除其 N 个会话（或改为禁止删除有会话的 Agent）
- 项目成员在线状态接入真实心跳（或下线该字段，避免误导）
- 操作审计：创建/改名/删除/取消记录操作者（可后置到 P2）

## 5. 接口变更一览

| 接口 | 变更 |
|---|---|
| `POST /api/auth/login` / `GET /api/auth/feishu/callback` | 成功后签发 `org_session` Cookie |
| `POST /api/auth/logout` | 删除 token + 清 Cookie |

## 6. 数据迁移

1. `sessions` 加 `created_by`、`last_message_at`（历史行置空）
2. `turns` 加 `user_name`、`agent_id`、`agent_name`；`status` 默认值调整；补 `UNIQUE(session_id, seq)`（历史重复先修复）
3. 新建 `auth_sessions`、`session_reads`
4. 历史 `sessions.agent_id` 保留但忽略
5. 启动时对账：`running` → `error`，重新计算会话状态

## 8. 验收标准

**P0**
1. 两个浏览器分别登录 A/B：A 发送后，B 能看到消息且发送者是 A（刷新后仍正确）
2. B 在 A 的 turn 运行中发送 → B 消息显示“排队中”，A 结束后自动执行，消息顺序与发送顺序一致
3. 非项目成员访问该项目会话返回 403；未登录访问任意 `/api` 返回 401
4. 删除会话会终止运行中的 turn，不再产生事件写入
5. 删除项目后其会话接口返回 404
6. 服务重启后不存在永久 `running` 的会话或 agent
7. 会话列表显示创建者，刷新后仍在

**P1**
1. 不刷新页面即可看到他人新消息、排队状态、agent 工作中状态
2. 未读数正确；打开会话后清零
3. 消息显示时间；失败 turn 有错误气泡
4. 长会话（100+ turn）打开时间可控，滚动加载历史
5. 两个会话同时运行同一 agent 时不互相覆盖文件（worktree 生效）

## 9. 明确不做

- 会话私有 / 邀请制成员（按决策：会话成员 = 项目成员）
- 按会话区分 agent 归属（按决策：项目内 agent 全可用）
- 输入中/在线状态、@ 通知、消息表情等社交功能（后续再评估）
- 工作流 / 自动化任务的队列化（仍在各自模块）
